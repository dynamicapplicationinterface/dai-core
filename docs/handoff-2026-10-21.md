### High

- **2a-H1. The runtime saves while an application transaction is held. A
  rolled-back row reaches the host's stored copy, comes back on reopen, and
  no log row carries it.**
  - **Traced.**
    - A `tx.run` inside `db.transaction` is a write, so it schedules the
      autosave (800 ms).
    - `flushAutosave` (`bootloader.ts:1089`) captures, seals and saves.
      Inside a transaction, `Changes.saving()` captures nothing
      (`changesets.ts:2383`, `if (this.inTransaction) return null`). The
      bytes are still taken and sent (`bootloader.ts:1135`,
      `saveState(exportDatabase(db), …)`), and they hold the transaction's
      uncommitted pages.
    - The application's later `ROLLBACK` (`bootloader.ts` `rollBackHeld`,
      `rollback`) schedules no save. So the stored copy keeps the row until
      something else writes.
    - The same holds for `saveDatabase`'s path (`:1198`) and for the
      shell's `PAGEHIDE` (`:3001`), which flushes whatever is held.
  - **Ran** (`interface.spec`, `ghost.spec`). An ordinary document in the
    runner: `base`, written and saved. Then
    `db.transaction(async (tx) => { await tx.run("INSERT … 'ghost'"); await sleep(3000–6000); throw … })`.
    The host's stored copy (`__runner.loadStored`, read in node) was read
    each second.

    | | Chromium | Firefox | WebKit |
    | --- | --- | --- | --- |
    | Stored while held | `base,ghost` from 1 s | `base,ghost` from 1 s | `base,ghost` from 2 s |
    | The application's promise | rejected, rolled back | the same | the same |
    | The live database after | `base` | `base` | `base` |
    | Stored 4 s after the rollback | `base,ghost` | `base,ghost` | `base,ghost` |
    | `_cs_log` ops naming `ghost` | 0 | 0 | 0 |
    | Reopened (the page reloads, the opener reopens from its store) | `base, ghost` | `base, ghost` | `base, ghost` |
    | After a later edit `later`, saved and sealed, A's file opened by B | B: `base, later` | the same | the same |
    | Page left 1.5 s into a held transaction (`goto` the runner) | stored `base,ghost` | the same | the same |

    The last row does not separate the `PAGEHIDE` flush from the autosave
    that had already run at 0.8 s. That the `PAGEHIDE` path takes the same
    bytes is traced only.

  - **Consequence.**
    - A transaction the application rolled back is the host's
      acknowledged ("Saved") checkpoint, and after a reopen it is the
      copy's state.
    - The row is outside the log: the R-S invariant, and D263's acceptance
      ("reopens with no row outside the log"), fail.
    - A's copy holds a row no other copy can ever receive. A and B diverge
      for good, and no merge or refusal says so.
    - R-Y's interface section asks that "unrelated requests cannot
      interleave inside an application transaction". The runtime's own
      save is one that does.
    - The pattern itself predates this build: a synchronous `BEGIN` held
      across an `await` would do the same. Build 2a makes it the taught
      primitive (`db.transaction`, in the model file), held for as long as
      10 s idle and indefinitely while the application keeps asking.
  - **Direction:** no bytes are taken while the connection is not in
    autocommit. A save that falls inside an application transaction waits
    for it to end, and a commit or a rollback of one schedules the save.
    On `PAGEHIDE` with a transaction held, roll it back first, then save.
    The red test is the probe above: the stored copy never holds the row,
    and a reopen shows `base`, on three engines.

### Medium

- **2a-M1. A rejected request can leave part of itself.**
  - **Traced.** A request of one statement runs without `BEGIN`
    (`bootloader.ts:3362`, `if (statements.length === 1 && !inside)`), and
    `runStatement` passes the SQL to `exec`, which runs every statement in
    the text. Nothing refuses a second statement in `db.run`, `query`,
    `get` or `value`, or in the kit's `data-run`, which goes through
    `data.run`.
  - **Ran,** three engines:
    `db.run("INSERT INTO notes (body) VALUES ('multi1'); INSERT INTO notes (body) VALUES (NULL)")`
    rejects with `SQLITE_CONSTRAINT_NOTNULL … notes.body`, and `multi1`
    stays.
  - **Consequence.** The promise says the request failed, and half of it
    landed. The model file says `db.run` "runs one statement". An author
    used to `exec`, or a `data-run` with two statements, meets this with no
    sentence. The old `exec` behaved the same way. The new interface makes
    "all of them, or none" its rule for `batch` and leaves the single
    request outside it.
  - **Direction:** refuse a request whose text is more than one complete
    statement (the `sqlite3_complete` split in `controlsTransaction`
    already finds them), naming `db.batch`. Or run a single request inside
    a savepoint as `batch` does.

### Low

- **2a-L1. Cancelling a request queued behind a running statement does not
  keep it from running.**
  - **Ran,** three engines. `first = db.batch([slow, slow])` (a recursive
    CTE, about 1 s), then `second = db.batch([q1, q2], { signal })`,
    aborted at 40 ms. `second` resolved and `q1, q2` were written.
  - **Traced.** The cancel is a port message (`bootloader.ts:3545`). The
    worker hears it only after the running statement returns. `pump`
    (`:3490`) starts the next queued request in the same microtask
    sequence, before the cancel's task is delivered.
  - The answer is truthful: the promise resolves with what ran. But
    "cancelled before it starts never runs" holds only while the worker is
    idle, which is the case the interface test holds (a held transaction
    waiting on a timer). Behind work, it is the case where cancelling
    matters.
  - **Direction:** yield one task before starting the next queued request,
    so a waiting cancel is heard first.
- **2a-L2. The interface's outcomes are documented in the code, not where an
  author reads.**
  - `website/docs/runtime-api.md` and the model file say nothing about
    `{ signal }`, the 10 s idle rollback and its sentence, or that a

    comments say, except 2a-L1.
