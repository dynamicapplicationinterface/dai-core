What changed against main:

- **The handle.** `await window.dai.openDatabase()` is `await
  window.dai.database()` everywhere it is named: STORE-IN-SQLITE,
  NO-INPUT-LOST-WHILE-OPENING (rule and why), the patterns, and the app.js
  example.
- **RESOLVE-BY-CALL.** `window.daiKit.conflict` and `resolve` are
  `await db.conflict` and `await db.resolve`.
- **The surface.**
  - Out: `db.exec(sql)`, `db.exec({ sql, bind })`, `db.selectObjects`,
    `db.selectValue`, `window.dai.exportDatabase(db)`.
  - In: `db.query`, `db.get` / `db.value`, `db.run` (returns
    `{ changes, lastInsertRowid }`), `db.batch` (all or none),
    `db.transaction(async (tx) => …)`, `db.export()`. Every call returns a
    promise.
- **requestShare.** Loses its `session` argument, which teaches an ordinary
  document nothing; it moved to the shared-tables entry.
- **"Refusals you may meet."** Removed. Its one entry, `NO_DOCUMENT_OPEN`,
  was for a shared write before `openDatabase()` resolved.
- **The patterns** are rewritten over `run`, `query`, `get` and `value`.
- **The kit.**
  - A form's button submits it, whatever its type.
  - `data-text` fills a field's value too.
  - `data-when` works on any element.
  - `data-run` runs on any element.
  - `<select data-options="SELECT id, name FROM people">` fills its options.

### WebKit offline: the emulation's, and what the document now does about it

- **F. The plain-page probe.** This was a page with no code of ours, under
  the driver's offline emulation. Chromium and Firefox load a blob script,
  a blob worker and a blob fetch; WebKit fails all three. The record is in
  `tests/worker-offline.spec.ts`'s header and `3ca39a61`'s message.
- **F. What it did to this build.**
  - The data's worker starts from a blob the shell mints out of the
    document's own verified glue. Nothing is fetched.
  - Offline under WebKit's emulation, that worker reported an error before
    its script ran. The shell refused the document on any worker error, so
    the refusal stood over the opener's menu and the data never started.
  - The application's own scripts are blobs too and fail the same way, with
    or without a worker. The refusal and the lost data were this build's.
- **F. The fix** (`3ca39a61`). The worker speaks first, as the frame does.
  - Its script posts `DATA_START` once it runs. Only then is it sent the
    engine, the stored database and the application's port.
  - A worker whose script never ran has been given nothing, so nothing is
    lost with it. It is started again from the same bytes on the next
    `online` and on a widening schedule (0.5 to 10 s), and said in the
    console.
  - A worker that ran and then failed still refuses.
  - The shell's facts say whether the data worker is starting or running.
- **F. The held test** (`tests/worker-offline.spec.ts`, two tests).
  - Test 1 goes offline once the document's shell is there. The opener's
    page says "loaded" before that, and going offline in between fails
    the shell's own blob load: the opener's mount, 2 runs in 8, not the
    document.
  - Test 2 holds the race: the first worker's blob is revoked before it
    loads, on every engine.
  - Both tests, three engines, five repeats: 30 of 30.

### Backlog

- **D288**, decided. An application's own SQL functions and callbacks are
  not part of the data interface. `db.createFunction`, a function among
  bound values, and a statement with any field but `sql` and `bind` are
  refused with one sentence. Shared-table documents keep the synchronous
  handle and its functions.
- **D289**, closed. A character outside the Basic Multilingual Plane in
  `schema.sql` stopped the build. The blanked copy is now built by UTF-16
  unit, and the `astral-default` vector carries such a default.
- **D290**, open. The next cold run asks the same ten prompts from the
  amended model file (33,959 bytes), fresh generations, and names the
  file's digest.
- **D291**, open, a non-gating reading. `ios-relaunch` 242 failed both
  attempts on Firefox in run 39727574866 (`a8cf5290`) and passes 12 of 12
  locally.
  - **I.** Likely cause, not confirmed: the iPhone first open waits on a
    mount whose ordinary document now starts a worker first.
