### What changed, and which anchor required it

One change, in `src/main.rs`:

- **The kept header's list.** The reader ignored `lists.json`, so it kept
  `merge-relabeled-list`'s header H under the list B stored (the case alone).
  That meant Ada's note was listed by no complete header and was refused
  `BATCH_DIGEST_MISMATCH`, and the dump's `_dai_batch` line carried the
  relabeled `covers`. Now the reader reads `lists.json` per copy, as it reads
  `verdicts.json` (a merge of B into A reads `b`'s). For a header it has an
  entry for, it uses that list both for which rows the header lists and as the
  `covers` it stores on the kept header.
  Required by `#merge-headers-kept-list` ("a kept header's stored `covers` is
  that list, not the one the sibling stored"), with `#verify-lists-tried` and
  `#fixtures-verdicts` (`lists.json` carries "the list that made a header
  authentic where it is not the one the header stores").

  The same list also feeds the revealing-header check
  (`#revealing-two-headers`), since that reads the lists of the headers this
  merge kept.

### Silences and ambiguities, and the reading taken

1. **A header the local copy already holds.** `#merge-headers-kept-list`
   says a kept header's stored `covers` is the signed list. When the local
   copy already holds that header id under a relabeled stored list, and the
   sibling holds it under another list, the page does not say whether the
   merge rewrites the local `covers`. Reading taken: no. The insert stays
   `INSERT OR IGNORE`, since the merge keeps the sibling's headers, and
   `#covers-cache` makes the stored list only a cache. No fixture reaches
   this.
2. **Own headers under a relabeled list.** `#equivocation-own-headers` counts
   a copy's own headers, but a merge verifies only the sibling's. The reader
   has no signature check, so it reads its own headers' lists from their
   stored `covers`. If a copy's own stored list were relabeled, the page
   gives no way to recover the signed list without verifying, and nothing in
   `lists.json` covers the local copy's own headers for this purpose. Reading
   taken: the stored list. No fixture reaches this.
3. **Scope of "reported nowhere but `AUTHOR_EQUIVOCATED`, whatever else it
   meets"** (`#report-silent`). The sentence sits among the admission reports
   (`SEAT_NOT_HELD`, `ENTITY_OTHER_SESSION`). Step 2's refusals are a
   different case: a row whose (author, seq) another table's headers
   equivocate, and which names a header that does not list it, could be
   `BATCH_DIGEST_MISMATCH` by `#merge-row-digest-mismatch`, which has no
   equivocation exception. The page does not say which rule wins.
   Reading taken: `#report-silent` governs the row set after placing (step
   4), and step 2's refusals stand. Such a row is not taken, so it never
   holds the id on this copy. No fixture distinguishes the two readings.
4. **The spelling of the signed list.** `lists.json` gives the list "in the
   one spelling". The reader stores that text byte for byte, and does not
   re-serialize it.
