### D170: a read-only mount offers no write

The application marks every control that writes shared rows `data-dai-write`.
When `dai.replicated.readOnly()` answers true, the kit disables each one:
every field of a marked form, and `inert` for an element that cannot be
disabled. A MutationObserver keeps them disabled, so a control drawn later,
or one the application's own draw enables again, is disabled before the page
paints. Chess, tic-tac-toe and request are marked, including the controls
they draw themselves (squares, conflict and name choices, answer boxes, save
and remove buttons). IDENTITY-BOOT-WRITES states the mark, and SESSION-CLOSE
points to it ("as on a read-only mount").

**Narrowed in `3f6ba21`.** The first build acted on `writable()` false. That is
also true of a copy opened with no host, or whose rules were refused, where
nothing over the document says why. The gate caught it: `examples-shared:244`
opens tic-tac-toe as a plain file, and its New game form could no longer be
typed in. The runtime surface gains `readOnly()`, which waits for the rules as
`writable()` does and answers whether the host mounted the copy read-only
(`mountReadOnly`, D108). The kit acts only on that, and a mount that is only
without rules keeps the application's own refusal sentence.

What counts as a write control: a control whose action writes a shared row
(through `dai.replicated` or the kit's seat calls), or opens the form that
does (New Game, Edit names). Local-only controls stay live: theme, animations,
the game list, photos (a local table), Invite (the host makes the share; the
export of a read-only copy still works, per `format-version-mount`).

`tests/read-only-writes.spec.ts`: each of the three, holding a batch format 1
header and a batch format 3 header, on a fresh device. The sentence is over
the document, `writable()` is false, the control a fresh copy is offered is on
screen (so the check is not empty), no control on the test's own list can be
pressed, and a scripted `insert` is refused with the sentence and lands
nothing. The list is the test's, not read from the mark, so a control an
application forgets to mark still fails it. Red first on all six (New Game,
Start and New request were pressable); green on Chromium and WebKit.

## Blind Rust level, 2 October

The Rust merge reader (`conformance/readers/rust-merge`) leveled to
docs/format.md as it now reads, built from the page, `conformance/merge/README.md`,
the fixtures (with `verdicts.json` and `lists.json`) and the crate's own source
only. Before: 55 of 59. After: 59 of 59, both directions, exit 0.

### What changed, and which anchor required it

1. **A held pending row adopts a held complete header**
   (`merge-row-held-signed`, `merge-no-adopt`). Before any row is placed, every
   row the local copy holds with `_r_batch` unset, listed (table, author, seq)
   by a header the copy held before the merge that is complete over the copy's
   own rows, gets `_r_batch` set to the lowest such header. Since the row is
   now signed, a signed row arriving at its id in another table no longer
   outranks it, and the two are both taken. Fixed
   `merge-held-row-signed` and `merge-seal-lost-pointer` (both `ab`, B into A) and
   `session-seat-not-held-after-merge` (`ba`). To do it, `merge` now takes the
   local copy's own verdicts and lists as well as the sibling's.
2. **A held header is rewritten to the list it signed**
   (`merge-headers-rewritten`). When step 1 keeps a header the local copy
   already holds under a different stored list, its `covers` is updated to the
   signed list. Before, `INSERT OR IGNORE` left the held list in place. Fixed
   `merge-held-header-relabeled`.

The other new anchors needed no change: `arriving-sibling` (the reader only
ever merges a sibling into a working copy), `parent-other-entity` (parents are
already looked up only in the row's own table and entity, and an equivocated
parent is caught first), `row-one-id` (already refused before placing or
rejected at placing), and `report-silent` (step 1 and 2 refusals are already
independent of admission, and late, void, waiting and parent-equivocated rows
were already silent).

### Silences and ambiguities met, and the reading taken

- **"Complete ... the header unverified."** For a header held before the
  merge, the page says complete is over the copy's own rows with the header
  unverified. This reader has no digest of its own, so it reads "complete" as
  that copy's `ok` in `verdicts.json`, as the merge README says. But `ok` is the
  TypeScript verifier's answer, and it includes authenticity. A held header
  that is complete but would not verify would be adopted by the page and not
  by this reader. No fixture tells the two apart.
- **Which list a held header adopts under.** `merge-row-held-signed` does not
  say whether a held header lists rows by its stored list or by the list it
  signed. Taken: the signed list (the copy's own `lists.json` entry where it
  has one, else the stored list), per the merge README and `covers-cache`.
- **A held header's own relabeled list, when the sibling does not bring the
  header.** `merge-headers-rewritten` sits in step 1, so it applies only to a
  header the sibling holds. A copy's own header stored under a list it did not
  sign, which the sibling lacks, is left as stored. Equivocation
  (`equivocation-own-headers`) is computed from the stored lists, both before
  and after the merge. So a rewrite in the same merge could, in principle, make
  an id look newly equivocated, or stop it looking equivocated, because of the
  cache rather than a new header. The page does not say which list a copy's own
  headers count under for equivocation. No fixture reaches this.
- **A received header that lists a held pending row whose arriving copy
  differs.** The page adopts through a received header only via "a row that
  arrives the same, a duplicate". Taken: when the arriving row differs, the
  held row stays unsigned and the signed arrival outranks it
  (`merge-signed-outranks`), as before.
- **When "before any row is placed" falls.** Adoption runs after step 1 and
  before step 2's classification. Classification does not read a held row's
  `_r_batch`, so placing it anywhere before step 3 gives the same result.
- **A held header refused `ROW_MALFORMED` on arrival.** It is not kept, so
  step 1 does not rewrite it. If the local copy already held it, the copy keeps
  what it held. The page does not say whether that counts as "kept". Left
  as is, and no fixture reaches it.

### D178, `sealed-leave:25` on WebKit: the runtime, fixed

**The counts on the old runtime** (`0cfda2e`, step 7b's runtime):

| run | WebKit | Chromium |
| --- | --- | --- |
| `sealed-leave:25`, traced | 11 of 20 failed | 20 of 20 passed |
| a probe copy logging every frame's sign, save and ack messages | 14 of 20 failed | 20 of 20 passed |

**The five steps, for seq 13** (Ada's e4, `moves`), the same in all 14
failing probe runs:

1. *The save that should have sealed it* is the move's own. The write queued
   it (800 ms debounce) while the new game's save was already sealing.
2. *Did the frame ask for a seal?* **No. This step breaks.** The new game's
   seal had listed its batches (seqs 1 to 9, and 10 to 12) and was waiting on
   the first signature when the move was written. It asked for seq 12 and
   seq 9, never 13.
3. *Did the host sign?* The two it was asked for, yes.
4. *Did the save land?* Yes, the one save, acked. It took its bytes after the
   move, so it holds seq 13 pending.
5. *Did the seal reach the stored copy?* None existed for seq 13. The stored
   copy holds it with `_r_batch` null, and no save is asked again.

**Why.** In `flushAutosave` (`src/runtime/bootloader.ts`), the seal's own
`recordSeal` is a write that queues a save, so the flush cancels a queued save
of the same database after the seal ("that save is this one"). The move's
queued save was that same database, and it was cancelled too. The losing timing:
the move lands after the new game's debounce fired and before its seal is done,
and the seal finishes inside the move's 800 ms. In the six passing probe runs,
the move landed before the debounce, and one seal took seqs 1 to 13. On
Chromium the move always landed inside the debounce. Why CI's WebKit passes
is not shown.

**Not the test.** Its counted save is the new game's (`before` was 0 in every
run), as D178's unproven reading said. But its 30-second wait for nothing
pending is exactly the invariant, and the runtime never saves again. The test
is unchanged except that its pending count moved to a helper the new test
shares.

**Fix** (one condition, one function): the flush cancels the queued save only
if no own row is left pending (`!hasPendingOwn()`). **Red first,** a new test
in `tests/sealed-leave.spec.ts`. It holds the new game's second signature at the
host and gives it back on the move's `DAI_HOST_AUTHORED`. On the old runtime:
Chromium 5 of 5 red, WebKit 2 of 5. Instrumented on WebKit, the three passes
were each rescued by a second save that started at the first one's ack and
sealed seq 13. What wrote to queue that save was not read. Holding the first
signature instead was red 3 of 3 and 1 of 3.

**On the fix:** both sealed-leave tests ×20 on WebKit and on Chromium,
**80 of 80**. `conformance/` regenerated (`--check` current, `run.py` 30 of 30),
`website/public/runtime/` restaged, and host shell `3e7e2f9f73a6d4e0`
committed. Full local Chromium + node: see the gates below.
