### Four checks jobs

`.github/workflows/test.yml`'s one `checks` job (35-minute wall) is four, in
parallel, each with its own wall:

| Job | Wall | Runs |
| --- | --- | --- |
| `checks-fast` | 15 min | drift (fixtures:check inside it), typecheck, build, dictionary, confusables, the Python reader, the Python merge reader, the Rust merge reader, `cargo test` and the replace-data example of `crates/sectioned` |
| `checks-holdout` | 30 min | `holdout.py` |
| `checks-properties-node` | 30 min | `properties.mjs` on Node 24; uploads its scenarios (`properties-scenarios`, kept one day) whatever it found |
| `checks-properties-python` | 30 min | `properties.py` over those scenarios |

**Each job builds for itself**, since `npm ci` runs `prepare`, and no job
passes dist/ to another as an artifact. Drift's rule (it regenerates `a.db`
and `b.db` in place, then puts the committed bytes back for every reader
after it) holds with no help: a job that never runs drift reads the committed
bytes from its own checkout. For the same reason fixtures:check is not a step
of its own. Run outside drift, it would leave regenerated inputs in the tree
for the readers after it.

**One dependency, by necessity:** `checks-properties-python` needs
`checks-properties-node`, because its input is the scenarios that job writes.
So three jobs run in parallel and the fourth runs after one of them. Its own
wall still holds, and if the node job leaves no scenarios, the download fails
and the job reads red.

**`scripts/ci-verdict.mjs`** lists the checks jobs with their times. It flags
a run that has some of the four and not all of them, and its summary line names
only the red jobs (pass C's M4, open since 5 October). It said "RED on
chromium, webkit and checks" whatever was red. Specs in
`tests/ci-verdict.spec.ts`. A run from before the split ("checks", one job) is
read as it stands.

**The push tier** (`npm run test:push`) runs the same checks in the same order:
`checks-fast`'s steps, then hold-outs, `properties.mjs`, `properties.py`. Each
check is named by its CI job in a failure line. It now also builds the
replace-data example, which it did not before. One difference, on purpose:
CI's `checks-fast` runs `npm run build`, which keeps a host, and a test run
never keeps one (D77), so locally the library is built by drift's first step.

### D199: the WebKit build race

`stamp-merge-digest.mjs` was the runtime config's `onSuccess` in
`tsup.config.ts`. tsup builds its three configs at once, so on a slow runner
the stamp read `dist/dai-merge.js` before the merge config wrote it (ENOENT,
no test ran): WebKit 1/4 in 37400386998, WebKit 2/4 in 37555780957. Now the
template copy, the stamp and the embed follow tsup in `npm run build:lib`, and
`build` and `build:all` call `build:lib`. Drift rebuilt every product and
nothing moved, so the order gives the same bytes. `npm run dev`
(`tsup --watch`) no longer stamps: use `build:lib` for a dist/ the runner can
use. Closed.
