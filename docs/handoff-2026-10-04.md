### H5: the egress rule (D181 closed), `52a7adb3`

The host keeps the id of every header of the person's that has left (a landed
save, a publish, a file the shell wrote after `LEAVE_CHECK`), one key-store
key per id (`leftHeaderKey`, `dai:left-header:<uuid>:<id>`), written in the
same transaction as the left floor (`claimLeave` in `apps/runner/src/opfs.ts`).
A header over a seq at or below the left floor leaves only if that header left
before; no leave carries two of the person's headers over one seq.

- A save **checks** before it writes and **records** once it lands (floor and
  ids together), so a save lost between the two leaves its headers uncounted
  and a re-seal of its rows still leaves.
- A file (`LEAVE_CHECK`) and a publish **claim**: check and record in one
  transaction, under the library lock, since they leave on the answer. A
  publish the rule refuses sends nothing, and the mailbox session says why
  (it used to let a throw from `beforePublish` escape).
- The stored copy at mount is **recorded**, as it was raised before.
- The seqs a header is held to are read by the host from the bytes
  (`leavingIn`, replacing `sealedTopIn`): its stored list and the seqs of the
  person's rows naming it, since either list can make it authentic. A
  published batch's are its rows' (`publishedLeaving`).
- Signing is unchanged: the host still signs over any seq above the floor.

Sentences: "This copy holds two different changes this device signed for the
same place in the document, so it was not saved or sent. Reopen the document
to go on." and "This copy holds a change for a place in the document that
this device has already sent, and that change never left, so it was not
saved or sent. Reopen the document to go on."

Page: `floor-egress` (format.md), a version line, and "What leaves" in
format-design.md. Backlog D181 closed.

Red first (`tests/left-floor.spec.ts`), shown red on Chromium **and** WebKit
before the host change (host change stashed for the WebKit red run):

- "a header held while the floor passed its seq does not leave": the document's
  code gets a signature over n above the floor and holds it; a header over
  n + 1 leaves in a file (floor n + 1); the held header written in is then
  refused by a save (the stored copy does not hold it) and by a file. Red:
  the save landed it.
- "two of the person's headers over one seq do not leave together, by save or
  by file". Red: the save landed both.
- "a re-seal after a lost save leaves, and so does every file after it":
  green before and after (a guard).

The save is asked through `__runner.exportContainer()`'s flush, before any
file write: a shell file write clears the frame's pending autosave, so an
export after it saves nothing (found while writing these tests).

**Reworked:** `tests/session-void.spec.ts` made the creator an equivocator
through exactly this path (her host's save carried both headers). Her host
still signs both; the test now writes them into a copy of her file in node and
reseals it, standing for a second copy of her store. Its subject (the kit's
void sentence and new game) is unchanged.

**Readings taken:**

1. "Under the same lock" read as the left floor's key-store transaction (one
   transaction moves both), plus the library lock on every path that held it
   for the floor already; the mount's record is not under the library lock,
   as its raise was not (a save holds that lock while it waits on the mount).
2. A save is a leave for the check as well as the record. Otherwise a held
   header could land in the store, be recorded as left, and then leave by
   publish over a seq whose other header had left.
3. A copy whose stored bytes already hold two of the person's headers over
   one seq (possible only before H5, from a hostile document) is recorded at
   mount and then refused every save: its document stops saving. Nothing
   honest produces it.
4. Ids that left before this change on a device are not in the record. The
   stored copy's are recorded at the next mount; a header that left only in a
   file whose save was lost, before this change, would be refused if written
   again. Version 2 has not left the sitting.

## D188: the contested-invite test (`36aa0204`)

One step: explain D188. The cause is in the test, and the test is fixed.

**Counts.** Chromium, `--retries=0 --repeat-each=10`, each commit built in its
own worktree (`npm ci` and `npm --prefix website ci`), run one after another:
`d894d1f2` 0 of 10 failed, `96554987` 8 of 10, `18e570d4` 5 of 10, every
failure "the joiner is still waiting to be seated". Green before R14, red

- Does the joiner's copy learn the new session id? **Yes.** It is in
  `games_current` on B's copy, with its open seat.
- Does its binding land in the new session? **On B's copy, yes; it never
  leaves B.** The creator's copy holds no binding in the new session, on any
  of 21 and 24 polls.
- Does the creator's confirm name the new session? **There is none to name
  it**, since no ask arrives. In the passing runs it does, and B is seated.

**Why it never leaves.** The test opens the new invite in a second tab on
device B while B's first tab is still open. In both failing traces the old tab
saved the stored copy 57 ms and 10 ms after the new tab mounted it. So the new
tab had been written past by another tab and, by D105, signed nothing: "seal
failed at <the new session's lane>: This document was written from another
tab since it was opened here". Its lane for the new session never published.
R14's repair is not wrong. The new flow just lacks the steps that used to
separate the old tab's last save from the new tab's read (this is a reading,
not measured).

**Fix.** `tests/mailbox-link-e2e.spec.ts`: B's old tab is closed before the
new invite opens (4 lines). 20 of 20 at `18e570d4` with it.

**Filed, open, under D188:** why the old tab saves just as the new one
mounts. If the mount is what asks for that save, a person who opens a new
invite while an older tab of the document is open gets a new tab that signs
nothing. Not read.

**How it was read** (for the next one): a probe in `letIn` (worktree only,
not committed) logged, on every poll, each session the joiner asked in, with
its `pendingSeat`, `mySeat`, open seat, own binding, holders, `_dai_close0`
and creator, and the creator's binders and holders for the same sessions. Then
the trace's console lines were read per `pageId`: the runner's lane and save
breadcrumbs ("lane for game", "watermark published at", "save N asked",

### Part 2: the checker, `cd08d2d7`

`scripts/properties.mjs` (the runtime) and `scripts/properties.py` (the Python
reader, over the scenarios the first writes to
`node_modules/.cache/properties/<vector>.json`). CI's checks job runs both
after `holdout.py`, on Node 24 (a second `setup-node`: node:sqlite's
`serialize`/`deserialize`; without them the script copies through files, about
2.5 times slower, tried locally with `--files`). Filed violations are in
`scripts/properties-known.json` with their backlog entry; an unfiled one fails
the run, and so does a filed one that no longer occurs. The Python side also
fails on any state, report or standing that differs from the runtime's.

How a vector is read: its **items** are one per header either copy holds,
taken from the copy that holds it complete, with the rows it covers; a header
no copy holds complete, or one refused, arrives alone. An **observer** (an
empty copy of the schema, replica `d0…`) takes items one merge at a time,
verified first. Every trial runs in a savepoint rolled back after, on one
connection per base, so the roster views compile once (with a fresh copy each time, 1,163
merges took 39 s on two vectors; the whole run is now 102,658 merges in
about 400 s, everything included).

- **P0.** Every order of the items (all up to 6, 50 seeded beyond): the same
  admitted dump (heads, holders, voided, equivocated, closed) and the same set
  of reports. Keyed `reports` when only the reports differ, `state` when what
  is admitted differs.
- **P1.** From three bases (copy A's items, B's, both): every mutation (for
  Ada, Bo and Cy; each gap, the next seq, the lowest and highest used; a
  seat row, a version of each of the author's seat rows naming each seat
  value, a binding, a confirm of each author, an author-table row for each
  value, a close, a version and a tombstone of each of his rows, a parent
  naming his own seq ahead and each other author's next, the second header
  alone at a used seq, and every seat-value type at his next seq and first
  gap). And **a header held and released later**: from every set of the
  vector's headers a copy can hold (all sets up to 8 headers, 64 seeded
  beyond), each header the set lacks, released alone. A removal is a lost
  hold, or a lost head that is no longer admitted: asked of the head view
  with every row naming it taken out (a version hides its parent without
  removing it). The first run counted every honest new version as a removal;
  that was the checker, fixed before any finding was read.
- **P2.** For each author with two headers over one seq and different
  digests: his standing (holds, heads, closed sessions) the same over every
  set of his conflicting headers that shows it (`chooses`), and (a reading,
  below) no set that shows it gives him a hold or admitted row that a smaller
  set short of showing it does not, rows only the added headers list aside
  (`gains`).

Counts at HEAD: 90 vectors, 13,037 orders, 15,117 mutations (2,064 not
writable: a roster table's CHECK refuses the value), 80 P2 subsets, 102,658
merges; node 6 to 7 minutes, Python 3 minutes.

**Readings taken:**

1. Rows no header covers are pending rows, not items: they never cross a
   merge (`BATCH_UNSIGNED`), and an order-dependent `BATCH_UNSIGNED` would be

2. P1's exemption is the brief's: any `AUTHOR_EQUIVOCATED` in that merge. A
   stricter one (only the reported author's rows, or his void session's) was
