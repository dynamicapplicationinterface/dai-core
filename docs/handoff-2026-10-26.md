### Observations

- **Separation between owners in one browser is not cryptographic, by
  design.** Every document's data key is kept unwrapped, extractable, beside
  its wrap, and each owner's key is held usable whoever is signed in. B's
  secrets open nothing of A's (item 1, below); any code in the opener's
  origin can still read every owner's data here.
- **The handoff's reading of the merge case does not hold on this tree.**
  "The host's setup check, not the runtime's flag, keeps that projection
  out": with the host's check removed (`considerKeepOffer` called with
  `authored === true` alone), `keep-offer.spec.ts` and
  `status-words.spec.ts` stayed green on three engines, 30 of 30, the
  merge test included. The runtime's flag alone kept that merge out.
- **`captureSave`'s `saved.ops === 0` arm cannot be reached.**
  `changes.save()` returns `null` for a batch with no operations
  (`changesets.ts:2451`), so `bootloader.ts:1408` reads `!saved`. Removing
  the arm and rebuilding left `keep-offer.spec.ts` green, 7 of 7: a mutation
  with no effect, not a test gap.
- **My MutationObserver witness for "Kept" missed the menu sentence** (it
  recorded only an HTML comment). H2 rests on direct reads of `#sheet-kept`,

### 1. Enrollment and the keys (Chromium, virtual authenticator with PRF)

**Ran** (`keys.spec`). A notes document typed into and saved; "Keep beyond
this browser" from the menu; the PRF output read by a second assertion of the
same passkey with `dai owner prf v1`; the keychain secret read where the
opener hands it to `navigator.credentials.store`; the wrapping keys derived
in the page from `docs/store.md`'s text, not imported.

- **The key store after enrollment:** `dai:data-key:<doc>` holds exactly
  `key` (AES-GCM, extractable), `owner`, `wrapped` (40 bytes);
  `dai:owner:<id>` holds `key` (AES-KW, **not** extractable, wrapKey and
  unwrapKey), `wraps` with exactly `prf` and `keychain` (40 bytes each),
  `credential`, `keychain` ("not offered": headless Chromium's `store()`
  throws, as the handoff says), `enrolled`; `dai:person-key` holds an ECDSA
  private key, not extractable, `sign` only.
- **The data key is wrapped under the owner key and nothing else.** The wrap
  opens with the held owner key, with the owner key from the PRF wrap and
  with the owner key from the keychain wrap, each to the data key's own
  bytes. It does not open under the PRF-derived key or the keychain-derived
  key directly (`OperationError` each). The raw bytes of the data key and of
  the owner key, as raw, base64, base64url and hex, appear in no OPFS file,
  no local-storage value and no IndexedDB value of any database (45 values,
  1 file searched).
- **The owner key is under exactly two secrets.** The PRF wrap opens with
  the PRF-derived key, the keychain wrap with the keychain-derived key, both
  to the same key; each refuses the other's key. The held key refuses
  `exportKey` and refuses being wrapped (`InvalidAccessError`).
- **The author key cannot be exported by any route found.** `exportKey`
  pkcs8, jwk, raw, spki: `InvalidAccessError`. `wrapKey` pkcs8 under
  AES-KW, jwk and pkcs8 under AES-GCM: `InvalidAccessError`.
  `structuredClone`, a `MessageChannel`, a dedicated worker (which then
  tried pkcs8 and jwk itself), a sandboxed opaque-origin frame (which tried
  pkcs8), and a put into another IndexedDB database read back: each copy
  arrived with `extractable: false` and refused export. The application's
  frame cannot reach the key store at all: `indexedDB.databases()` there is a
  `SecurityError` (origin `null`).
- **A second owner in the same browser unwraps nothing of the first's.**
  After `leave()`, a second document typed into and enrolled from the menu
  as B. With B's PRF output, B's keychain secret, B's held owner key and B's
  owner key from its PRF wrap, every attempt on A's PRF wrap, A's keychain
  wrap and A's document's data key: `OperationError`. B's own document opens
  under B's key; A's held key does not open it. A's data-key record was
  byte-for-byte unchanged by B's enrollment, and the two owner keys differ.
  With A's passkey removed from the authenticator, `signIn(A)` answered
  "cancelled" and the owner stayed B; `signIn()` unnamed opened B.
