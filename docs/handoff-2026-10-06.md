### Found on the way

- **Listed by some held header was not enough.** The first build counted a
  row any held header listed. The property pass found 22 P0 violations, one
  vector, both readers agreeing: `session-relayed-header-lost-save`, where
  the copy holds a relayed header without its row (a lost save) and a forged
  row written at that id counted. Built instead as above: the header the
  row's `_r_batch` names must list it, which every row a merge takes
  satisfies and no row written by SQL does unless it names one.
- **D196, filed.** What the views cannot check: the copy's own `_dai_batch`
  as it stands. A header written into it by SQL, never verified, covers rows
  and feeds `_dai_equivocated`; a row written by SQL at a listed id, naming
  that header, counts whatever its content. Neither travels.
- **The ruling's last sentence and the code.** It says the runtime's own
  unsealed rows "are not admitted until sealed, as today". No view reads
  `_r_batch`, before this step or after: a copy's own pending row counts in
  its own views at once (an own move shows before the seal). What was built
  is what the ruling instructs, that those rows are unchanged; the backlog
  records the sentence as given and says so. Whether own pending rows should
  stop counting until sealed is not decided here.
