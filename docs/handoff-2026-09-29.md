## The conventions copied from Git's format documentation

Read from Git's `Documentation/` on master (the files are `.adoc` now, not
`.txt`): `gitformat-pack`, `gitformat-index`, `gitformat-signature`,
`gitprotocol-v2`, `technical/hash-function-transition`,
`technical/commit-graph`.

**What the format pages hold, and the conventions copied into `format.md`:**

1. A short description first: what the thing is and what a reader does with
   it, before any layout (gitformat-pack's DESCRIPTION).
2. Page-wide conventions stated once, before the layouts ("All binary
   numbers are in network byte order"; which hash): here, hex and base64url
   spelling and UTF-8 order, at the top of Identifiers.
3. Layouts as indented blocks, one field per line, width and encoding
   first, meaning on the indented line under it (the pack header, the index
   entry): the canonical row and the canonical header.
4. An order is named by its comparison ("memcmp() order, no localization"):
   UTF-8 order, defined once.
5. Valid values enumerated, and what is invalid named ("Type 5 is reserved
   ... Type 0 is invalid"): the one shape of parents and what is malformed.
6. Versions described in place by number, with no history narrative and no
   dates ("Version 2 pack-*.idx files ..."): the version history is one line
   per change.
7. MUST and MUST NOT only where an implementer could otherwise choose, as
   gitprotocol-v2 uses them ("A server MUST wait ...", "Clients MUST NOT
   require state"); the format pages otherwise state layout declaratively.

**What the format pages leave out:** why, the alternatives, who decided and
when, links to discussion. Not copied: gitformat-pack's occasional one-line
asides ("Observation: ...", "This is new in v2 so ...").

**What the technical/ pages hold instead, and `format-design.md` copies:**
Objective, Background, then the design, and "Alternatives considered", each
alternative its own subsection saying what it was and why not, with dated
references to commits and threads (hash-function-transition); design details
and related links (commit-graph). Adapted as asked: each section is the
problem, the rule chosen (linked to its anchor) and the alternative
rejected, rather than one "Alternatives considered" block at the end.
