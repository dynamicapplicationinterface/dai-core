# Code review — 6 September 2026

Scope: everything except `website/`. Read in full: the container core
(`src/core.ts`, `container.ts`, `cose.ts`, `cbor.ts`, `format.ts`, `schema.ts`,
`inline.ts`, `store*.ts`, `identity.ts`, `x509.ts`, `publisher.ts`,
`trust.ts`, `kit.ts`, `lint.ts`, `bundle.ts`, `mcp.ts`, `compile.ts`,
`browser.ts`, `env.ts`), the runtime (`src/runtime/bootloader.ts`,
`src/template.html`), the opener (`apps/runner/**` including the service
worker, middleware and presign endpoint), the desktop host (`apps/desktop/**`,
`src-tauri/src/lib.rs`, `crates/sectioned`), and CI.

Where a finding could be checked against a running system, it was. Those are
marked **verified**. Everything else is from reading the code.

Severity is about consequence to a person using this, not about how clever
the bug is.

---

## Summary

The cryptographic core is in good shape. The signed set is reconciled in both
directions, the envelope carries its algorithm in the protected header, the
payload is detached and rebuilt by the verifier, hosts build their own shell
around a verified archive and run the application in a frame with no origin.
The isolation story is real and is tested by a probe. That is the hard part,
and it is done properly.

The problems are at the edges that were built in the last two days, and they
are the ones a public deployment feels first:

1. **The public store is an anonymous file host.** The presign endpoint binds
   neither the size nor the content of what gets uploaded. Verified: a 1 KB
   declaration accepted a 64 KB upload, stored under a name that is not its
   hash, served publicly. This is the one to fix before anything else.
2. **Identity verification can be forged** by anyone who can obtain an
   ordinary Sigstore certificate, because the chain walk does not check that
   intermediates are CAs and the Rekor entry is not bound to the presented
   certificate. Not yet reachable in production — the public opener ships no
   roots — but it is shipped code and the spec §9.5 describes it as sound.
3. **Trust is pinned before consent.** The opener records a document's key
   the moment a link is followed, before the card is shown. A link nobody
   opened can therefore make the real document read as an impersonation
   later, and there is no UI to undo it. The service worker's share target
   makes this reachable from any web page with no click.

Then a Windows-only path-check bypass in the MCP server, a privacy gap in
what the store publishes regardless of consent, no CSP or frame-ancestors on
the opener, and a handful of correctness bugs.

**Fixed on this branch, with tests, for review before merge:** H1 (size,
digest and cache-control signed into the presigned URL; icon cap enforced),
H3 (pins made only on Open; cross-site share labelled), M1 (the path-check
bypass), M6 (cache-control on presigned uploads), M7 (`checkTrust` split).
H1 has since been verified closed against production — see its section.
H2 fixed after merge: CA constraint in the chain walk, logged-signer check
as §9.5 check 5, in both readers, with four new conformance vectors.
M2 fixed after merge: the sidecar carries size, clear and consented preview
only. M3 fixed after merge: CSP with `frame-ancestors 'self'` and no
`script-src` (a `blob:` frame would inherit it). M4 and M5 fixed after
merge: early refusals reach the opener; the mount timeout is 30 s and not a
verdict. M8 fixed. **Not fixed here:** the lows.

## High

### H1. The presign endpoint makes `store.opendai.app` an anonymous file host — **verified**

`apps/runner/api/presign.ts`, `src/store-s3.ts` (`presignPut`).

The presigned PUT signs only `content-type` and `host`, with
`x-amz-content-sha256: UNSIGNED-PAYLOAD`. So:

- **Size is not enforced.** The `size` the caller declares is checked
  against `MAX_BYTES` and then discarded. Verified against production: a
  request declaring 1,024 bytes was granted a URL, a 65,536-byte body was
  accepted (`200`), and is now served at `store.opendai.app/bbbb…bbbb`.
  Nothing stops 5 GB.
- **Content is not bound to the name.** The key is `sha256` of nothing in
  particular; R2 stores whatever arrives. Verified: the object at
  `bbbb…bbbb` has SHA-256 `156c3844…`. The opener refuses it (hash mismatch),
  but the raw URL serves it to anyone, as `application/octet-stream`, from
  your domain.
- **The icon cap is not enforced.** `kind: "icon"` is granted up to
  `MAX_BYTES` (5 MB), not `ICON_CAP` (100 KB). Verified: a 4 MB icon presign
  returned `200`. It is served as `image/png` from your domain.
- **The sidecar is not validated either.** `admit()` runs only inside
  `presignedStore`, i.e. in the uploader's own browser. A hand-written
  request skips it. The store's "admission" is a client-side courtesy.
- **The rate limit is per-instance memory** (acknowledged in the code). It
  resets on cold start and does not exist across regions.
- **CORS is `*`**, so any website can mint upload URLs from a visitor's IP.

Consequence: anyone can host arbitrary bytes at
`https://store.opendai.app/<64 hex>`, 20 per hour per IP per instance, with
no record of who. For a public relay that is a legal and abuse exposure, not
a theoretical one.

**Fix, in order of leverage:**

1. Sign `content-length` into the presigned URL (add it to
   `X-Amz-SignedHeaders` and the canonical headers) and return it in the
   `headers` the client must send. S3-compatible stores reject a body whose
   length differs. That enforces the cap.
2. Sign `x-amz-content-sha256: <hash>` (the real value, not
   `UNSIGNED-PAYLOAD`). S3 verifies the payload against it; R2 documents
   support for it — **confirm on R2 before relying on it**, and if it turns
   out not to be enforced, the fallback is a small validator (a Worker on an
   R2 event notification) that HEADs each new object, hashes it, runs
   `admit()`, and deletes what fails.
3. Cap `kind: "icon"` at `ICON_CAP` server-side.
4. Sign `cache-control: public, max-age=31536000, immutable` too — see M6.
5. Add `x-amz-meta-uploader-ip` (or a hash of it) as a signed header so an
   abuse report can be acted on.
6. Replace the in-memory counter with a Durable Object / KV counter, or
   accept it as a speed bump and rely on 1–2.

**Done on this branch: 1, 2, 3 and 4**, in `src/store-s3.ts` (`presignPut`
now signs `content-length`, `x-amz-content-sha256`, `cache-control` and
returns the headers the uploader must send), `apps/runner/api/presign.ts`
(the sidecar and icon must declare their digest; the blob's *is* its name;
the icon is capped at `ICON_CAP`), and `src/store-presigned.ts` (computes
and declares both). `tests/presign.spec.ts` holds it.

**Verified closed in production, 6 September.** Against the deployed
endpoint and the real bucket, after the CORS rule gained `PUT` (it allowed
only `GET` and `HEAD`, which would have refused every browser upload at the
preflight):

| case | result |
|---|---|
| honest upload, declared size and digest | `200`; read back with `cache-control: public, max-age=31536000, immutable` |
| body whose digest differs from the signed header | `400` — R2 verifies `x-amz-content-sha256` |
| body whose length differs from the signed header | `403` |
| the original attack: 1 KB declared, 64 KB sent | `403`, nothing stored |

So the bucket itself enforces both bindings and no validator is needed. One
correction along the way: the first cut put the digest in the canonical
request's hashed-payload slot, which query-string signing fixes at
`UNSIGNED-PAYLOAD`, and every upload came back `SignatureDoesNotMatch`. The
digest belongs in the signed header, which is where the bucket checks it.

Cleanup: `bbbb…bbbb` (64 KB, junk) has been deleted. The two chore charts
(`effec267…`, `f4997d72…`), one PNG and a 26-byte object (`7c05c410…`) are
end-to-end test objects; delete when convenient.

### H2. Identity (§9.5) can be forged with any legitimately obtained Sigstore certificate — **fixed**

`src/x509.ts` (`chainsToRoot`), `src/identity.ts` (step 4).

Fixed: `mayIssue()` (basicConstraints cA, keyUsage keyCertSign) gates every
hop in `chainsToRoot`; `verifyIdentity` step 5 requires the hashedrekord's
`spec.signature.publicKey.content` to be the presented leaf byte for byte
(or its SPKI); §9.5 states both; `dai_read.py` mirrors both; conformance
vectors `identity-ca-intermediate` (shown), `identity-non-ca-issuer`,
`identity-other-certificate`, `identity-unlogged-certificate` (absent).
Item 3 (validity-window sanity) was not done: with 1 and 2 in place the
leaf is one a held Fulcio issued, and its window is that Fulcio's choice.

Two gaps that together let an attacker present a certificate for any
identity — `ceo@bank.com`, say — and have the card say "Signed in as":

- `chainsToRoot` verifies each hop's signature but never checks that a
  non-leaf certificate is a CA (`basicConstraints cA=TRUE`, `keyUsage
  keyCertSign`). Any Fulcio **leaf** — which anyone gets by logging into
  GitHub or Google — can therefore act as an issuer for a certificate the
  attacker writes themselves.
- Step 4 checks only that the Rekor entry's logged *signature* equals the
  manifest's. It does not check that the logged *key or certificate* is the
  presented leaf. Rekor will log a signature made with any key, so the
  attacker gets a genuine Rekor entry for their own signing act, then pairs
  it with a forged leaf that names somebody else and carries the attacker's
  key.

The forged leaf's validity window is attacker-chosen, so the "integratedTime
within validity" check passes.

Exposure today: the public opener and desktop ship no roots, so `verifyIdentity`
returns `absent` everywhere. The moment a root list is provisioned — the
enterprise scenario the feature exists for — this is live.

**Fix:**

1. In `chainsToRoot`, require every certificate above the leaf to carry
   `basicConstraints` with `cA=TRUE` and `keyUsage` including
   `keyCertSign`. Refuse otherwise.
2. In `verifyIdentity`, parse the Rekor body's `spec.signature.publicKey.content`
   (a base64 PEM certificate or key) and require it to equal the presented
   leaf certificate (or its SPKI). The SET is over the body, so this binds
   the log entry to the certificate.
3. Sanity-check the leaf: Fulcio issues ~10-minute certificates; a leaf with
   a multi-day window is not one. Cheap, and it turns a forgery into a loud
   refusal.
4. Update spec §9.5 to state 1 and 2 as requirements; the Python reference
   reader should implement them too, which is what the conformance suite is
   for.

### H3. The opener pins trust before the person has agreed to anything — **verified by reading**

`apps/runner/src/main.ts` (`ingest`: `checkTrust` at line ~529, `showCard`
at ~595), `src/trust.ts` (`checkTrust` pins as a side effect),
`apps/runner/public/sw.js` (share target).

`checkTrust` records `documentUuid → key` on first sight and returns. In
`ingest` that happens before the card is shown. So following a link is
enough to pin — pressing "Open it" is not required, and closing the tab does
not undo it.

Attack: the UUID of a document is public (it is in every link's sidecar,
see M2, and in any copy of the file). An attacker builds a container with
that UUID, signs it with their own key, and gets the victim to *load* — not
open — a link to it. From then on the genuine document, when it arrives,
is refused as "signed by a different publisher… treat it as an
impersonation." The trust signal is inverted, and because the attacker's
document was never added to the library there is no Delete button to reach
`forgetTrust`. The pin is permanent from the UI.

The service worker widens the door: `POST /shared` is accepted from any
origin (a plain cross-site form post), parks the file, and redirects the
victim into the opener with `?shared=1`, which ingests it. No click needed —
an auto-submitting form on any page the victim visits. The card then says
"Shared to this app", which reads as something the person did.

**Fix:**

1. Split `checkTrust` into a pure `trustVerdict()` and an explicit
   `pinTrust()`. Pin only after "Open it" — the same rule `recordPublisher`
   already follows, and for the same reason. **Done on this branch.**
2. The share target cannot be gated at the worker. I first wrote a check on
   `Sec-Fetch-Site` there, and the test posted straight through it: that
   header is attached by the browser *after* a service worker has seen the
   request, so a worker never sees it, and `Origin` is added at the same
   layer. What a worker does see is the referrer, which a page can withhold.
   So the worker now records the posting origin and the card says "Posted
   into this app by <origin>" instead of "Shared to this app"; with 1 in
   place, a cross-site post is reduced to what a link already is — a card,
   and nothing recorded unless the person presses Open. **Done on this
   branch**, with a test that posts from the website's origin.
3. Give orphan pins a way out: list pins that have no library entry in the
   sheet, or clear them with the document's Delete. Less urgent once 1 is
   in, since a pin can no longer be made without an Open — but pins from
   before this fix may already exist on devices.

The desktop host has the same pin-before-mount ordering in `gateOnTrust`,
but there opening *is* the consent, and there is no drive-by route to it.

## Medium

### M1. MCP `withinRoot` is bypassed by another drive or a UNC path on Windows — **verified**

`src/mcp.ts` line ~210.

```
ALLOWED  "D:\\evil\\startup.html"      -> D:\evil\startup.html
ALLOWED  "\\\\server\\share\\x.html"   -> \\server\share\x.html
```

`path.relative` across drives returns the absolute target, which does not
start with `..`, and `resolve(root, rel)` reproduces it, so both checks pass.
A model-driven `outputPath` can write anywhere the user can. Symlinks inside
the root are not resolved either.

**Fix:** refuse when `path.isAbsolute(rel)`; resolve with `realpathSync`
before comparing. **Done on this branch**, with a Windows-only test for the
drive and UNC cases.

### M2. The public sidecar exposes the whole manifest regardless of preview consent — **verified, fixed**

`src/store.ts` (`Sidecar`, `sealForStore`), `store.opendai.app/<hash>.json`.

The consent design says "off is real": no preview object, nothing to serve.
But the sidecar is publicly readable at a URL every chat server sees, and it
carries `manifest` in full — `appName`, `favicon` (709 bytes of SVG in the
test), `publisherName`, `generator.model`/`provider`, `createdAt`,
`hashes`. Preview OFF only stops the *middleware injecting* the name; anyone
with the link's path can `GET` it. The comment in `store.ts` acknowledges the
operator can read the manifest; it does not say the internet can.

**Fix:** the sidecar should carry only what the middleware needs — `preview`
(when consented), `size`, `clear`. Nothing today reads `sidecar.manifest`
after admission, and with presigned uploads the store never ran `admit()`
anyway. Drop it.

Fixed: `Sidecar` is now `{size, clear?, preview?}`; `admit()` keeps the
hash, size, cap and preview-shape checks and no longer verifies a manifest;
§3 states what a sidecar MUST NOT carry. Objects already in the bucket keep
their old sidecars until they expire or are deleted.

### M3. The opener has no Content-Security-Policy and can be framed — **fixed**

`apps/runner/vercel.json`, `apps/runner/index.html`.

No CSP header or meta; no `frame-ancestors`; no `X-Frame-Options`. The opener
origin holds every document a person has opened (OPFS + IndexedDB, in the
clear) and their trust pins. The code uses `textContent` and `setAttribute`
carefully, so I found no injection — but there is no second line of defence
for the one origin where it matters most, and any page can frame it for
clickjacking.

**Fix:** in `vercel.json` for `/(.*)`:

```
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none';
  base-uri 'self'; frame-ancestors 'none'; frame-src 'self' blob:;
  worker-src 'self'; connect-src 'self' https:; img-src 'self' data: blob:
```

`connect-src https:` is needed for `?open=` and `#u=` links to arbitrary
stores; everything else can be tight. Check the playground handoff popup
still works (it posts to a different origin; CSP does not govern postMessage).

Fixed, with one deliberate deviation from the header above: no `script-src`
and no `default-src`. The cartridge is a `blob:` document, and a blob
document inherits its creator's policy; the shell inside runs one inline
script under a per-mount nonce that a static header cannot name, so a
`script-src` here would be inherited and stop every document. The header
sends `frame-ancestors 'self'`, `object-src 'none'`, `base-uri 'self'`,
`form-action 'self'`, `connect-src 'self' https:` (plus loopback, for a
store on the person's own machine and for the suite), and media directives
that are a superset of the shell's <meta> policy — pinned by
`tests/website-headers.spec.ts`, which also checks the superset property
against `src/template.html` so a shell change cannot be silently narrowed.
`X-Frame-Options: SAMEORIGIN` beside it. Getting a `script-src` on the
opener page means serving the cartridge from a real URL through the service
worker, with its own headers, instead of a `blob:` — a follow-up.

### M4. Refusals sent before the handshake are silently dropped by the opener — **fixed**

`apps/runner/src/main.ts` (`DAI_HOST_REFUSED`, `fromMountedContainer`),
`src/runtime/bootloader.ts` (`refuse`, `boot`).

`fromMountedContainer` requires `mountedNonce`, which is set only on
`DAI_HOST_HANDSHAKE`. The bootloader sends the handshake *after* every check
passes, so any refusal raised before it — payload, manifest, digest,
signature, `NO_APPLICATION`, most `BOOT_FAILED` — arrives with the nonce in
its payload and is discarded. The comment above the handler says the
opposite. In practice the opener has verified the container itself so these
are rare, but when they happen the person sees a blank frame.

**Fix:** for `DAI_HOST_REFUSED`, accept when `event.source ===
cartridgeFrame.contentWindow` and either `mountedNonce` is null or the
nonces match. Add a test that mounts a shell which refuses early.

Fixed as described, in the opener and the desktop host (which had no source
check on a refusal at all). `tests/early-refusal.spec.ts` mounts an
unsigned container with `app/index.html` removed from archive and manifest
together — the opener's verifier passes it, the shell refuses
`NO_APPLICATION` before its handshake — and holds that the refusal is said
and a forged one from another window, or with the wrong nonce, is not.

### M5. `MOUNT_TIMEOUT` at 5 s is a refusal, and the target device is a slow phone — **fixed**

`src/runtime/bootloader.ts` (`HANDSHAKE_TIMEOUT_MS`), `main.ts`.

On a mid-range Android the base64 decode, unzip, digest and mount of an
850 kB container can exceed five seconds. When it does, the bootloader
posts `DAI_HOST_REFUSED`, the opener removes `loaded` and shows "could not be
opened" — and then the application finishes mounting underneath it. The UI
is now inconsistent, and the number 5.1 measures is the one that trips it.

**Fix:** treat the timeout as a status line ("still starting…") rather than
a refusal until something much longer (30 s), and never remove `loaded` for
it. The shell already has `watchBoot()` for exactly this tone.

Fixed: the shell says "still starting" at 5 s, `watchBoot`'s advice at 20 s,
and refuses `MOUNT_TIMEOUT` at 30 s; the opener says a timeout without
removing `loaded`, so a boot that then finishes is not underneath a message
saying it failed.

### M6. Presigned uploads carry no `Cache-Control` — **verified**

`cache-control: null` on the read-back of an object uploaded through
`/api/presign`. `s3Store.putObject` sets `immutable`; `presignPut` does not
sign the header, so browsers and the desktop app never send it. Every open of
a browser-published document refetches it, and `scripts/check-store.mjs`
would fail on it.

**Fix:** sign `cache-control` in `presignPut`, return it in `headers`, send
it from `presignedStore`. Same change as H1 step 4. **Done on this branch.**

### M7. `checkTrust` pins as a side effect

`src/trust.ts`. Root cause of H3 and a footgun for any future host: a
function named "check" that writes. **Split on this branch** into
`trustVerdict` (reads) and `pinTrust` (writes); `checkTrust` remains as the
composition for hosts where looking and agreeing are the same act.

### M8. The kit's `data-text` writes `.value` on elements that have one but do not show it — **fixed**

`src/kit.ts` (`fill`): `if ('value' in target && target.tagName !== 'OPTION')
target.value = text`. `HTMLLIElement`, `HTMLButtonElement`, `HTMLProgressElement`,
`HTMLMeterElement`, `HTMLDataElement`, `HTMLParamElement` all have `value`.
`<li data-text="title">` — a natural thing to write — sets `li.value`
(a number) and shows nothing. A model given the recipe will hit this.

**Fix:** whitelist `INPUT`, `TEXTAREA`, `SELECT` for the value path.

Fixed, on both the fill path and `:typed`; `tests/kit.spec.ts` holds
`<li>`, `<button>` and `<data>` showing text and `<input>` taking a value.

## Low

- **L1. CBOR decoder has no depth limit.** A crafted envelope of nested
  arrays throws `RangeError`. Caught on the signature path; `countersignaturesOf`
  would reject rather than throw. Add a depth cap of ~32.
- **L2. CBOR decoder accepts duplicate map keys** (last wins) although
  deterministic encoding forbids them. Harmless because protected-header
  bytes are signed as bytes, but a strict verifier should refuse.
- **L3. Bootloader and host reader disagree on v3 `hashes` omissions.**
  `authoritativeDigests` accepts a v3 container whose `hashes` omits a signed
  entry; the bootloader's `verifyPayload` refuses it. Pick one; the spec
  comment says omission is allowed.
- **L4. Save filename is `document.title` unsanitized.** Browsers strip
  separators, but a title of `..` or a 300-character name is passed through.
- **L5. Desktop `DAI_HOST_REFUSED` handler has no source or nonce check.**
  The application inside the frame can post it and eject itself. Harmless,
  but inconsistent with the opener; add the check.
- **L6. Desktop `tauri.conf.json` has `"devtools": true` and the CSP lacks
  `base-uri`, `object-src`, `form-action`.** DevTools in a release build is
  unusual for shipped software; the CSP gaps are defence in depth.
- **L7. Rust `read_cartridge*` accept any absolute path.** Only host code
  calls them, but restricting to paths the user chose (dialog or argv) costs
  little and removes a class of future mistakes.
- **L8. `.bak` and `.dai-save` files leave plaintext copies beside a
  document.** Correct engineering for durability; worth a sentence in the
  desktop docs, since a person who deletes a document may not expect a
  sibling to survive.
- **L9. The home-screen `start_url` carries the decryption key into OS PWA
  metadata.** By design for 3.5; document that an installed icon is a copy
  of the key.
- **L10. `admit` accepts `manifest.hashes === null`** (`typeof null ===
  "object"`).
- **L11. The inline carrier drops countersignatures** — the unprotected
  header is not carried. Say so in the spec's carrier section.
- **L12. MCP staging directories under `tmpdir()` are never removed.**
- **L13. `bundle.ts` `checkPath` does not reject NTFS alternate data streams
  (`name.txt:stream`), reserved names (`CON`, `NUL`) or trailing dots.**
  The compiler writes these to disk in the MCP path.
- **L14. A container framed by a hostile page will hand that page its
  document on save.** Acknowledged in `bootloader.ts`; exposure is limited
  to containers served over HTTPS and framed cross-origin. Worth restating in
  the security doc as a reason not to host `.dai.html` files on a web server
  you do not control.
- **L15. `escapeHtml` in `core.ts` leaves `'` alone.** The template only uses
  double-quoted attributes, so it is fine today.
- **L16. DNS prefetch / preconnect / prerender are a channel CSP does not
  govern.** The linter refuses to seal them, which is the right layer for a
  browser host; the desktop webview could block them at the network layer
  and does not yet. Noted in the code, noted here.

## What is done well, so it is not accidentally undone

- Signed-set reconciliation in both directions (`checkSignature`), including
  the `runtime/schema.json` case that motivated it.
- Detached COSE_Sign1 with the algorithm in the protected header; the
  verifier rebuilds the payload rather than trusting the envelope.
- Hosts assemble their own shell around a verified archive; the publisher's
  bootloader never runs with a host origin.
- The application frame has no origin: no `allow-same-origin`, no popups,
  no top navigation, nonce'd CSP, Trusted Types for kit-only apps, and a
  probe that holds every claim on the card against what the frame can do.
- Every `postMessage` that matters checks `event.source`, and the ones that
  write to storage or disk also require the session nonce.
- Atomic saves with `fsync` before rename, a generation counter, and an
  advisory lock; a registry that fails closed on corruption.
- The published test key is refused by the compiler and labelled by hosts.
- `.env*` hygiene is enforced by a test rather than by a paragraph.
