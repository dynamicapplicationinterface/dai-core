### What landed

For every document the compiler builds with no session policy:

1. **Capture.**
   - The compiler appends the changeset log to the schema:
     `-- dai:replicated CREATE TABLE _cs_log (payload BLOB NOT NULL)`
     (`src/changes-log.ts`, `src/core.ts`). So the document is an ordinary
     version 4 replicated document that `requires` authorship and
     replicated, with no new manifest field and no new capability.
   - The frame starts the session extension once the schema block has run,
     before the seed blocks (`startChanges`, `src/runtime/bootloader.ts`).
   - Every save, automatic or explicit, captures first, then seals, then
     saves (`captureSave`). The changeset is one `_cs_log` row, written by
     `createEntity`, so it is the payload of an ordinary signed batch.
     Batches, seq, floors and equivocation are unchanged, and
     `src/replicated-batch.ts` verifies as before.
   - A merge captures this copy's unsaved changes before it admits
     anything.
2. **Keys** (`src/changesets.ts`).
   - An INTEGER PRIMARY KEY is rewritten to an author-ranged id. The author
     index is in bits 32 to 52, the counter in bits 0 to 31, and the
     largest id is 2^53−1.
   - `last_insert_rowid()` is overridden.
   - A text key takes a uuid.
   - A table with no primary key is keyed by a ranged rowid. The session
     extension's `SQLITE_SESSION_OBJCONFIG_ROWID` captures it.
   - A literal id is the lint finding `literal-id` (a warning), whose fix
     says to omit the id.
   - **A.** The author index is 21 bits of the author id, never 0, until
     R-E's enrollment exists. Two authors of one document share a range
     with probability about n²/2^22. If they do, nothing is lost: the same
     id from two authors is one row, column-merged and flagged.
3. **Merge policy.** The spike's literal policy, ported as written:
   - different rows merge, and different columns of one row merge;
   - the same column written concurrently keeps both values, shows the
     later by (lc, author), and marks the row `pending`;
   - delete against update keeps the row, flagged `delete-conflict`;
   - a later local edit to a flagged row clears the flag on every copy.
   - The flags are rows of `_cs_flag(tbl, pk, kind, detail)` in the stored
     document, which the host can read from the bytes it holds. There is no
     sheet yet.
4. **Runtime rules.**
   - Seed blocks run once, at document creation (`runSeedsOnce`, recorded
     in `_dai_meta`). A copy that arrived carries the record, and its rows
     come from the log.
   - App triggers stand down while merged rows are applied: they carry
     `WHEN dai_projecting() = 0`, added when a table is adopted.
   - `PRAGMA foreign_keys = ON` at open.
     - **F.** No example declares `REFERENCES`: `grep -ci references` over
       every `examples/*/schema.sql` is 0. So none breaks, and none needed
       fixing.
     - The full suite and the ten apps ran with it on.

### High

**PR9-H1. Lost write in the merge's verify window.** The merge captures
first (`bootloader.ts:1511`, `captureSave(liveDb)`). Then it awaits
`verifyBatches` (`:1514`), commits, and projects (`:1543`). The application
can write during the await. Projection pauses the session
(`changesets.ts:193-202`, `:706-726`). But the session extension stores only
a row's first old value and reads the *current* value when the changeset is
generated (`:211`). So a row the application changed in the window is
captured at the next save holding the projected value. Its bases name the
remote version, as if the person had chosen it.
- Ran (P2). A and B share an item, "Tent". A sets "A-remote". B does what
  the frame does: save, verify, then `UPDATE items SET title = 'B-local'`
  inside the await, then admit and project, then save:
  `shownAfterProject: "A-remote"`. B's log now holds
  `["items", …, "title", "b14b…:1", "A-remote"]`. The cells hold "Tent",
  "A-remote" (A) and "A-remote" (B). **"B-local" is in no cell, on no
  copy.** `flags: []`.
- This breaks R-O ("never … discards conflicting changes"), with nothing
  flagged. The same leak follows any paused runtime write to a row the
  session already holds, including the save's own re-projection at
  `:585`, which runs after `take()` and so is safe today.
- The fix belongs to the frame: no application write may land between the
  capture and the projection. Alternatively, re-capture after the commit and
  before projecting.

**PR9-H2. R-F as written is not what was built.** R-F's text, set beside the
code:
- *"The same record, different fields: merge only where the app declared
  the fields independent."* Every column merges with no declaration
  (`stateOf`, `changesets.ts:748-758`). S2 (`merge-policy.spec.ts:44`)
  asserts the unconditional merge.
- *"An unresolved value is pending and does not feed calculations."* The
  later value is written into the application's table (`place` → `write`,
  `:830-832`), so every `SUM`, join and filter reads it. S3 (`:51`) asserts
  that one value shows.
- *Rejected: "showing an arbitrary winner with a flag."* Showing one value
  by (lc, author) with a `pending` flag is that alternative. R-F's evidence
  calls the author-id tie "to the person … arbitrary".
- R-F puts row granularity at V1.2 and checkpoint granularity at V1.0.

The review question lists "different columns merge; … shows later by (lc,
author)" as R-F. That wording is the spike's policy (handoff 19 October,
"Merge policy. The spike's literal policy, ported as written"). Either R-F is
amended to the spike's policy, or the policy changes. Today the code and the
ruling disagree, and the tests assert the code.

Per clause, the test and whether a weaker implementation would pass:

| Clause | Test | Weaker implementation passes? |
|---|---|---|
| Different rows merge | S1 (`:20`) | Yes, any merge does. Row ranges are asserted. |
| Different columns merge | S2 (`:44`) | No. Row-level last-writer-wins fails `missing`. |
| Same column keeps both, flags pending | S3 (`:51`), S5b, S5c | No for "keeps both" (`pending` detail holds both values). |
| …shows the later by (lc, author) | S3, S5c | **Yes.** Both accept either value (`toContain`). Any deterministic tie-break passes. |

| A later local edit clears the flag everywhere | "S3 resolved" (`:62`) | **Yes** for "clear every flag on the row at any save". No test edits a *different* column and checks that `pending` stays. |

**PR9-H3. `last_insert_rowid()` answers another table's id.** The override
(`changesets.ts:379-386`) keeps one slot, `{rowid, id}`, set by the
`_cs_id_<table>` trigger (`:458-460`). It returns the slot's id whenever the
connection's real last rowid equals the slot's hidden rowid. Hidden rowids
start at 1 in every table, so they coincide all the time.
- Ran (P1). `CREATE TABLE lists (id INTEGER PRIMARY KEY …)`,
  `CREATE TABLE tags (k TEXT PRIMARY KEY …)`, then in one transaction insert
  a list, then a tag: `{"lir":1666975591825409,"tagRowid":1,"listId":1666975591825409}`.
  Inside a transaction that inserts into two tables, `last_insert_rowid()`

  id becomes a foreign key, and nothing fails.

  reading the wrong id.

**PR9-H4. The counter is read before the log is projected.** `Changes` sets

## Data-interface catalog (external review)

Astra's response of 19 October, pasted verbatim. Each row's id (C01…,
K01…, D01…, T01…, S01…, Q01…, M01…, P01…) is the stable reference used by
the tests, the backlog and later handoffs.

---

Yes. The rest of the class is bigger than “SQLite features the session extension misses.” It includes every place where SQLite’s observable behavior, captured history, and merged state can disagree.

I would make the conformance contract:

A supported operation must retain its documented SQLite behavior locally; every durable application-state change must be captured under the correct author; replay must not invent additional application effects; and merging must not silently turn valid transactions into invalid application state. Unsupported cases must fail before an apparently successful save.

Below is the catalog I would give engineering. These are failure modes to test and required outcomes, not assertions that your current implementation contains every defect.

I also ran small probes against SQLite 3.46.1 in this environment—not your shipped WASM build. They reproduced three especially important behaviors:

* Disabling a session during an incoming update does not stop that update leaking into a later changeset for a row already touched by the session.
* Disabling ordinary triggers does not disable TEMP triggers.
* A changeset can be extracted from an open transaction and contain changes that subsequently disappear on rollback.

Those need early vectors.

1. Capture coverage and provenance

The first invariant is stronger than “we attached a session”:

Every supported persistent write route is covered, and the captured changes belong only to the local capture epoch—not to intervening remote application or runtime bookkeeping.

SQLite sessions are associated with a particular database on a particular connection. They record a net difference, and extracting a changeset does not reset the session. Their behavior is not equivalent to an ordered SQL operation log. 

ID / feature	What can go wrong	Required behavior and vector
C01 — Tables without a declared primary key	Successful writes produce no captured rows under the default session configuration.	Check coverage before accepting persistent writes. Modern SQLite offers SQLITE_SESSION_OBJCONFIG_ROWID; configure it before attaching tables, or provide a stable identity mechanism. Test identical duplicate rows, deletion of one duplicate, and subsequent merge.
C02 — NULL in a primary key	Ordinary rowid tables can allow NULL in non-rowid-alias primary keys. Sessions skip those rows. Moving a key into or out of NULL can appear as only an insert or delete.	Require a proven identity path for these rows or reject NULL-key writes. Test single and composite keys, including one NULL component and NULL→non-NULL→NULL transitions.
C03 — WITHOUT ROWID	Code assumes an integer rowid exists, reads undefined hook rowid arguments, or assigns ranged IDs to a table that has no rowid allocation.	Capture using the declared primary-key tuple. Preserve its ordering and types. Inserts must not change last_insert_rowid(). Test composite keys whose PK order differs from column order.
C04 — Virtual tables: FTS, R-tree, custom modules	Ordinary session capture does not provide general virtual-table replication. Capturing internal shadow tables as ordinary app tables can reproduce an invalid internal structure.	Declare each supported module’s contract. For derived indexes, replicate authoritative content and rebuild the index through a controlled path. For authoritative virtual-table content, provide a tested adapter or reject its use.
C05 — Generated columns	The wrapper treats generated columns as writable, misaligns column indexes, or uses an older session implementation that cannot handle them.	Pin the SQLite version and use generated-column-aware metadata. Test both STORED and VIRTUAL columns, interspersed with ordinary columns. Replay base values and obtain the correct generated values without synthesizing writes to generated columns.
C06 — Tables created after capture starts	A fixed attachment list misses new tables; CREATE TABLE AS SELECT also creates a keyless table unless handled.	New persistent tables must acquire a verified capture contract before their first durable contents are accepted. Test dynamic creation, immediate insertion, and creation inside a transaction that rolls back.
C07 — Incoming writes while capture is disabled	A locally touched row is later changed by replay. Extraction reads its current contents, and the incoming value is attributed to the local author.	Close and durably preserve the local capture epoch before modifying its underlying database with remote state, or use genuinely isolated state with an explicit rebase. Disabling the session alone is insufficient.
C08 — Incremental BLOB writes	A wrapper watching SQL statements misses sqlite3_blob_write(). Hook code may misread its preupdate notification as a deletion.	Exercise the actual BLOB API against the shipped session build. Test partial overwrite, repeated writes, rollback, handle invalidation, and save with an open handle. Never permit raw storage mutation outside the capture contract.
C09 — A second writable connection	A session on connection A misses writes made by connection B, although both modify the same database.	Every writable handle must be enrolled in one capture/commit protocol, or application access to additional writable handles must be prevented. Test writes from a second worker and connection.
C10 — Preupdate-hook replacement	A helper installs its own preupdate hook and disrupts session capture.	The runtime must own hook registration. SQLite explicitly disallows independently registering a preupdate hook on a handle with sessions. Test attempted hook replacement through every exposed API.
C11 — “Indirect” changes	Trigger/FK-produced changes are dropped as “not user changes,” or the indirect flag is mistaken for proof that a change came from replay.	Capture persistent effects of local triggers and FK actions. Preserve provenance separately: SQLite’s indirect flag is not an authenticated origin marker or complete dependency graph.
C12 — Net-zero work	Insert→delete, update→revert, and delete→reinsert are mistaken for an operation history.	Define these as state-difference capture, unless a separate operation log exists. Test insert→delete producing no net row, and delete→reinsert at the same key becoming an update. Do not claim that every intermediate user action survives.

Important version corrections: optional rowid capture exists; generated-column session support was added in SQLite 3.49.0; and WITHOUT ROWID support is not generally absent. Your conformance baseline must name the exact engine and enabled options, not rely on older blanket limitations. 

C07 is particularly dangerous. SQLite documents that an enabled-session change to one field followed by a disabled-session change to another field can produce a changeset containing both. I reproduced exactly that.  Incremental BLOB notifications and hook ownership also have explicit special rules. 

2. Primary keys, rowids, and author-ranged allocation

Overriding last_insert_rowid() does not, by itself, make ID rewriting transparent. The allocated identity is observable through constraints, foreign keys, triggers, RETURNING, rowid aliases, and subsequent SQL.

SQLite also distinguishes a true INTEGER PRIMARY KEY rowid alias from other integer-affinity primary keys. WITHOUT ROWID changes the semantics again. 

ID / feature	What can go wrong	Required behavior and vector
K01 — Exact primary-key syntax	A text rewrite confuses INTEGER PRIMARY KEY, INT PRIMARY KEY, BIGINT PRIMARY KEY, composite PKs, and the special DESC cases. Test column-level and table-level declarations, quoted identifiers, comments, ASC/DESC, STRICT, and WITHOUT ROWID.
K02 — Omitted ID versus NULL versus explicit values	The allocator rewrites an explicitly supplied 0, negative number, or business key as though it requested an automatic ID. K03 — Explicit imported keys	Importing records or applying remote changes allocates new IDs, breaking references and signatures.	Import/replay must retain the captured keys. A genuine collision becomes an explicit conflict; it is not silently renumbered.
K04 — Allocation through indirect SQL	Top-level INSERT rewriting works, but a trigger, INSERT … SELECT, multi-row INSERT, or UPSERT insertion bypasses it.	Every row that requires automatic allocation must use the same allocator. Test all write paths, including nested triggers.

K08 — Range collision and exhaustion	Truncated author fingerprints collide; a counter wraps; restoring an old database reuses a previously issued range.	Force collisions and exhaustion in tests. K09 — Multiple contexts sharing an allocator	Two tabs or cloned contexts allocate from the same author range without coordinated counters. K10 — Integer precision	A correct 64-bit SQLite ID becomes an inaccurate JavaScript Number, JSON value, signature input, or bound parameter. Local view writes execute their INSTEAD OF triggers normally. Capture affected persistent base tables; replay base effects without reinvoking the view. Test a view writing several tables.
T03 — FK CASCADE / SET NULL / SET DEFAULT	Trigger suppression does not establish that FK actions are suppressed. Applying a captured parent operation creates additional child changes.	Define exactly-once FK effects. Evaluate SQLITE_CHANGESETAPPLY_FKNOACTION where available, or an equivalent controlled application strategy followed by validation.
T04 — Deferred FKs, cycles, and RESTRICT	Replay order encounters temporary violations or rejects a valid final state; alternatively invalid final state is admitted.	Stage the complete effect group and validate the final FK graph. Test child-before-parent, cycles, deferred constraints, RESTRICT, and parent-key changes.
T05 — RAISE variants	RAISE(IGNORE) is treated as rollback, although earlier changes can remain; FAIL/ABORT/ROLLBACK are collapsed together.	Capture exactly the effects surviving SQLite’s result. Test a trigger writing an audit row before each RAISE variant.
T06 — Recursive triggers and UPDATE OF	Recursive effects are missed, replay loops, or changing a value to itself is incorrectly considered incapable of producing trigger effects.	Capture actual persistent effects under pinned recursion settings. Test nested triggers, UPDATE OF, unchanged assigned values, recursion limits, and rollback.
T07 — BEFORE-trigger undefined cases	Runtime behavior is specified using SQLite behavior that is itself undefined.	Reject unsupported patterns or state that no deterministic compatibility guarantee covers them. In particular, test BEFORE triggers modifying/deleting their target and reads of unassigned NEW.rowid.
T08 — Trigger-maintained summaries	Base rows merge correctly, but independently captured totals/counts no longer equal the merged base data.	Derived state needs a declared recomputation/validation contract or an explicit pending conflict. Do not mark a stale summary settled merely because each column merge succeeded.
T09 — Validation triggers	Source transactions were validated locally, but the merged state bypasses validation because replay suppresses triggers. A malicious signed batch can exploit the same gap.	Separate side effects from admissibility checks. Validate the merged candidate without blindly rerunning effectful triggers. Test a trigger enforcing a cross-row invariant.
T10 — External side effects from triggers/UDFs	An email, connector call, or other external action runs twice, or runs for data that later rolls back.	Do not perform irreversible actions inline as ordinary replayable SQL effects. Use a host-authorized, transaction-linked outbox and independently idempotent delivery.
T11 — Triggers touching runtime tables	Application writes forge batches/frontiers; or a malicious trigger attached to a runtime table executes when trusted runtime bookkeeping occurs.	Protect both writes to and triggers on runtime-owned objects. Validate imported schema before trusted operations. Test indirect writes, views, TEMP triggers, and a trigger fired by the runtime’s own outbox INSERT.
T12 — Restoring suppression state	An exception leaves triggers/FKs disabled for subsequent local work, or reenables capture before replay finishes.	Restore all connection policy in guaranteed cleanup; if restoration cannot be verified, discard the connection and fail closed. Inject failures at every application step.

TEMP-trigger behavior is explicitly documented.  Writable views, RAISE, and BEFORE-trigger restrictions need their own vectors rather than being treated as ordinary INSERT cases.  FK actions and changeset application have separate controls from ordinary triggers. 

A particularly important T08 vector

Initial state: no workout entries; summary.count = 0.

Device A inserts workout A; its trigger writes count = 1.

Device B inserts workout B; its trigger writes count = 1.

After merging, both workouts exist. Both captured summary values agree on 1.

There need not be a same-column conflict, yet the correct count is 2.

That is why “capture everything, suppress triggers, merge columns” is not a general solution for arbitrary trigger-maintained derived data. Agreement of captured values does not establish an invariant.

5. Schema evolution, namespaces, and maintenance

A changeset is not a complete schema contract. Its table metadata is insufficient to establish matching column meaning, collations, constraints, generated expressions, or application validation rules. 

ID / feature	What can go wrong	Required behavior and vector
S01 — Runtime ALTER TABLE	An active session contains old-layout records while extraction or application uses a new layout.	Establish a schema-epoch boundary. Close the prior capture epoch, perform an authorized migration, and restart capture with new metadata. Otherwise refuse the DDL before mutation. Test add/rename/drop and rollback of each.
S02 — DROP and recreate under the same name	Old changes apply to a logically unrelated new table with the same name and compatible column count.	Give table incarnations/schema epochs distinct identities. Test delayed old batches after drop/recreate.
S03 — Changed column order or meaning	(price, quantity) is treated as compatible with (quantity, price) because counts and key positions match.	Bind batches to an authenticated schema definition and explicit compatible mapping. Name/count checks alone do not pass.
S04 — New indexes and constraints	A UNIQUE, partial, or expression index changes admissible state without changing ordinary columns.	Include semantic constraints and required functions/collations in compatibility checks. Test a previously valid batch against a newly introduced constraint.
S05 — Different app releases writing concurrently	Old and new clients produce changes using different defaults, units, columns, or validation.	Define accepted schema-version combinations and migration directions. Preserve incompatible batches as blocked/pending, not silently coerced or dropped.
S06 — ATTACH / DETACH	Capture covers main but writes occur elsewhere; only one database is exported; cross-database transactions lose atomicity. S07 — TEMP tables and name shadowing	Runtime SQL reads a TEMP table with the same name as a protected main table. Temporary work is accidentally exported or persistent work is omitted. 6. Transactions, capture epochs, and save sequencing

“Clear capture only after the batch is logged” is necessary but insufficient. You also need to define what happens while extraction, signing, logging, persistence, and acknowledgment are in flight.

ID / feature	What can go wrong	Required behavior and vector
Q01 — Transaction held across a save	Extraction publishes changes from a transaction the app later rolls back.	Never publish or acknowledge those changes as committed state. Defer/refuse the save or expose a precisely defined draft state. Do not silently COMMIT an application-owned transaction.
Q02 — Nested SAVEPOINTs	Capture is cleared on RELEASE even though an outer transaction can still roll back.	Only a committed outer boundary is eligible for publication. Test nested names, repeated names, ROLLBACK TO, inner RELEASE, and outer rollback.
Q03 — Partial rollback	Rolling back one savepoint discards unrelated earlier capture or leaves rolled-back changes captured.	Compare extracted changes against the actual surviving committed state. Include earlier committed work in the same capture epoch.
Q04 — Failed COMMIT / automatic rollback	Runtime assumes a transaction is still open—or committed—based only on the SQL it issued.	Inspect actual SQLite state after failures. Test BUSY, deferred-FK failure, FULL, IOERR, NOMEM, and INTERRUPT.
Q05 — Commit hooks	Runtime runs SQL/extraction inside a non-reentrant hook, or treats the commit callback as evidence that commit completed.	Hooks may signal work; they are not the place to run reentrant database operations or report durable completion. Verify success after the relevant engine operation finishes.
Q06 — Cumulative extraction	A second extraction republishes earlier changes because sqlite3session_changeset() did not reset the session.	Identify capture epochs explicitly. Test two successive saves with no intervening edit, then one new edit.
Q07 — Edit during asynchronous signing/logging	A new edit joins the old session, then clearing that session discards it; or the batch digest describes a different state from the saved bytes.	Freeze/rotate safely with an immutable extracted payload and an unambiguous next epoch. Test writes at every await/yield boundary.
Q08 — Remote apply between local edit and extraction	Already touched rows absorb remote values despite temporarily disabled capture.	Seal/preserve the local epoch before replay or use a proven isolated rebase. Test local edit column A, remote edit column B, then local save. Only A may be attributed locally.
Q09 — Database saved, batch log missing	A crash preserves new business rows but loses their signed history/capture, so later recovery treats unlogged state as settled.	Application state and its recoverable log must have an atomic or explicitly recoverable commit protocol. A SQL INSERT into an in-memory log is not a durable log acknowledgment.
Q10 — Batch logged, database save missing	Acknowledged local state cannot be reconstructed, or a retry signs a different batch over the same identity.	Recovery must replay the durable immutable batch or retain the prior acknowledged state. Reuse the exact logged batch identity/bytes, not newly generated timestamps or signatures.
Q11 — Log succeeds, capture reset fails	The next save signs the same changes again as new work.	Persist enough epoch/frontier information to identify already logged effects after restart. Inject failure immediately before and after session replacement.
Q12 — Concurrent saves	Save A clears state that Save B still needs, or B’s older snapshot overwrites A’s newer one.	Serialize the state transition, not just final file writes. Test overlapping saves with new edits between them.
Q13 — Applying a remote batch and marking it received	The cursor/applied marker advances before data and pending conflicts are durable.	Commit materialization, pending-conflict evidence, and the received/applied frontier together or through a recoverable protocol. Received, processed, and materialized are distinct states.
Q14 — Disconnect, close, cancel, worker termination	Cleanup loses capture, retains disabled policies, or assumes a rollback hook fired on close.	Test every termination boundary. Reopen into a coherent acknowledged checkpoint or a reconstructible pending state. Session objects must be disposed before their connection.

SQLite’s transaction state, savepoint behavior, and hook restrictions support these distinctions.

7. Merge semantics and invariant preservation

This is where your stated policy—columns merge, competing same-column values become pending, delete/update is retained—needs additional rules.

The central distinction: preserving all captured evidence is not the same as producing a valid materialized database.

ID / feature	What can go wrong	Required behavior and vector
M01 — Causal order versus value comparison	A later intentional edit is mistaken for a concurrent conflict, or an old batch overwrites a causally later edit because old values happen to match.	Track causal dependencies independently of field values. Test reordered delivery, repeated values, and 0→1→0 histories.
M02 — Different-column CHECK violation	Two locally valid edits merge into an invalid row.	Validate the combined candidate. Example: CHECK(start <= finish), initial (0,10), A sets start=8, B sets finish=5. Preserve both proposals as an explicit constraint conflict; never expose (8,5) as settled.
M03 — UNIQUE / partial / expression indexes	Independent rows collide only after merge; first arrival wins and another valid edit disappears.	Preserve the competing evidence and use deterministic constraint-conflict handling. Test same email under different PKs, partial uniqueness, and expression indexes.
M04 — Unique-value swaps	The final changeset is valid but naïve row-by-row application fails because no first update satisfies uniqueness.	Support a staged application strategy that can realize the valid final state. Test swapping two unique values via a temporary source value. Do not OMIT one update to “make progress.”
M05 — Parent delete versus concurrent child insert	No same-row conflict exists, yet the combined graph has an orphan or silently loses a new child through cascade.	Treat this as a relational conflict. Preserve both changes; resolve the dependent component under a specified policy.
M06 — Transaction split by conflict handling	One half of a transfer applies while the other becomes pending.	Preserve transaction/effect-group atomicity where required. Record transaction boundaries during capture or conservatively group the capture epoch; the final changeset alone does not reconstruct original transaction boundaries.
M07 — Increment/decrement idioms	Two count=count+1 operations from 0 both capture 1; merging equal values yields 1, not 2.	Do not infer arithmetic intent from before/after values. Use an explicit operation-aware contract where counters are promised; otherwise document/register-conflict semantics. Test increment versus literal assignment producing the same changeset.
M08 — Conditional writes and read dependencies	WHERE NOT EXISTS, inventory checks, and “only one active item” logic pass independently offline and jointly violate intent.	Do not claim distributed serializability from write capture alone. Require an enforceable constraint, declared validation/coordination, or an explicit pending outcome for such operations.
M09 — Delete/update and resurrection	Tombstone evidence disappears after compaction, allowing an old update to resurrect deleted state, or deletion hides a conflicting update.	Retain the causal information required by the stated delete/update policy. Test delete-first, update-first, stale restore, and post-compaction delivery.
M10 — Pending values used as ordinary input	An arbitrary displayed winner feeds UPDATE x=x+1, a calculation, or a trigger, silently converting ambiguity into a new “resolved” value.	Define how applications read pending cells and how writes acknowledge observed alternatives. A routine write must not accidentally resolve unseen conflicts.
M11 — Resolving while another conflict arrives	A resolution erases an alternative it never observed.	Resolution must name the alternatives/heads it actually resolves. A concurrent unseen alternative remains represented. Test three writers and all delivery orders.
M12 — Missing row / missing dependency	NOTFOUND is treated as an irrelevant no-op even though the insert simply has not arrived.	Distinguish satisfied deletion, missing prerequisite, malformed operation, and stale incarnation. Preserve and retry valid pending dependencies.
M13 — Changeset conflict callbacks	OMIT silently loses work; REPLACE is used for unsupported conflict types; a callback reads row data where none is supplied.	Map every SQLite conflict code to your policy explicitly. Persist omitted-as-pending operations separately. Test DATA, NOTFOUND, PK CONFLICT, other CONSTRAINT, and FOREIGN_KEY independently.
M14 — Unchanged versus SQL NULL	A missing new.* pointer is serialized as NULL, erasing an untouched column.	Represent “not included” separately from a SQL NULL value. Test updates setting NULL beside untouched NULL and non-NULL fields.
M15 — Type-sensitive values	INTEGER, REAL, TEXT, BLOB, and NULL collapse through JS/JSON; key lookup and signed-byte verification diverge.	Preserve SQLite storage classes and exact supported values. Test 1, 1.0, '1', X'31', empty text/blob, embedded NUL, and numeric boundaries.
M16 — Text keys and collations	SQLite considers two keys equal while the merge map considers them different—or vice versa.	Match the declared key equality contract, including affinity, composite keys, NOCASE, RTRIM, and pinned custom collations. Preserve original value spelling separately from identity comparison.
M17 — JSON and BLOB fields	The merge invents nested semantic merging for what SQLite stores as one column.	Default to the declared column policy. Test concurrent json_set() calls on different paths: those are still writes to one SQL column unless a richer contract explicitly exists.
M18 — Undo / inverse changesets	Applying an inverse blindly undoes another device’s later work.	Treat undo as a new operation against the current causal state, with conflict handling—not as unconditional physical rollback of shared history.
M19 — Duplicate delivery and equivalent effects	A retry triggers effects again, or equal values are used to erase distinct author evidence.	Deduplicate by authenticated operation/batch identity. Equal final values may share a materialized result without discarding their distinct provenance.
M20 — Physical byte equality	Replicas with identical logical contents are declared divergent because insertion order, page layout, or VACUUM differs.	Compare canonical logical state, conflict state, schema, and causal frontier for convergence. Use file digests for the integrity of a particular snapshot, not as a universal logical-equivalence test.

Some particularly sharp API traps are documented: SQLITE_CHANGESET_REPLACE is valid only for certain conflict types; at an end-of-apply foreign-key conflict, returning OMIT can commit changes including FK violations; and newer apply flags have explicit behavior for FK actions and unique-value update loops. 

An omitted UPDATE value is a NULL pointer, not necessarily a SQL NULL.  SQLite’s affinity, collation, and STRICT rules must remain part of the value contract. 

Three things the changeset cannot tell you

These are design decisions, not bugs an additional SQL parser patch automatically fixes:

Intent. SET count=count+1 and SET count=1 can yield identical captured state differences.

Read dependencies. A transaction may depend on the absence of another row; that absence is not a captured write.

Derived meaning. A stored total of 1 does not explain which source rows justified it.

Your merge engine therefore needs a stated boundary between generic state merging and application invariants requiring declarations, validation, or coordination. Otherwise “ordinary SQLite” becomes an accidental promise of distributed serializability.

9. Turn this into vectors with stronger oracles

A SQL snippet plus “both replicas have three rows” will miss most of this class.

For each supported feature, record the following evidence.

Oracle	Required assertion
Local SQLite equivalence	Same observable behavior as the pinned native SQLite reference: values, types, errors, transaction state, row counts, and trigger effects. Normalize only explicitly permitted ID-allocation differences—not unrelated semantic differences.
Capture completeness	Replaying the captured local effects into the appropriate baseline reproduces the committed authoritative application state. No missing table or surviving trigger/FK effect.
Capture provenance	Remote application and runtime bookkeeping cannot become newly authored local changes.
Replay isolation	Incoming application causes no additional effectful app-trigger/UDF execution.
Invariant validity	Settled materialized state passes declared constraints. Incompatible evidence survives as a defined pending conflict, not an invalid settled database.
Convergence	All permitted delivery permutations produce the same canonical state, pending alternatives, and causal result.
Crash recovery	Every acknowledged save is recoverable; partial work is either reconstructible or explicitly unacknowledged. No orphaned “saved” rows without their required log.
Retry idempotence	Duplicate delivery, lost acknowledgment, and restart do not create new effects or conflicting re-signatures.
Authority	App-controlled SQL, schema, and callbacks cannot modify or impersonate protected runtime state.

Then apply these cross-product axes, not just one happy-path fixture per row:

* Origin: direct SQL, trigger, writable view, FK action, secondary handle, supported BLOB API.
* Outcome: success, no-op, ignored row, partial FAIL, statement ABORT, transaction rollback, savepoint rollback.
* Timing: before extraction, during signing, after logging, during persistence, before acknowledgment, before capture reset.
* Delivery: A→B, B→A, three-writer permutations, duplicate, delayed prerequisite, stale restored client.
* Schema: current, compatible additive revision, incompatible revision, same-name recreated table.
* Recovery: normal reopen, worker termination, storage failure, old checkpoint, wiped context with a new author.

Not every combination is meaningful, but pairwise coverage plus deliberately chosen three-way interactions will find substantially more than another review organized around individual syntax features.

10. What I would prioritize before the next review

I would make these the first red vectors:

1. Dirty local capture + disabled-session remote update of the same row.
2. TEMP trigger firing during replay despite trigger suppression.
3. Save inside an open transaction, followed by rollback.
4. Local edit arriving while the previous extracted batch is being signed/logged.
5. Two independent inserts plus a trigger-maintained aggregate that agrees on the wrong result.
6. Different-column merge violating a CHECK constraint.
7. A transaction partly materialized because one change became pending.
8. REPLACE deleting a parent and triggering child effects.
9. High remote IDs followed by local AUTOINCREMENT allocation and restore.
10. Runtime outbox writes invoking application-controlled schema.

The architectural issue I would resolve first is the capture-epoch boundary. It must make one thing mechanically true:

A signed local batch describes an immutable, committed set of local effects from a known schema and causal baseline. Nothing arriving remotely, nothing written by runtime bookkeeping, and nothing occurring after extraction can accidentally become part of that authorship.

After that, the next major boundary is valid materialization: the engine may retain all conflicting evidence, but it must not present a merged database as settled when its constraints or declared derived-state relationships no longer hold.

Those two contracts cover much more of the class than another collection of fixes for particular SQL statements.

### The rulings

- **R-S, the capture-epoch boundary.** A signed batch is an immutable,
  committed set of local effects. A save waits for the application's
  transaction (`sqlite3_get_autocommit`). The epoch is logged and the
  session rotated before any remote apply. The apply runs with no
  application TEMP trigger on the connection.
- **R-T, valid materialization.** Merged state is never settled while a
  declared constraint fails. Intent, read dependencies and trigger-kept
  derived values are not inferred.
- **R-U, the engine pin.** The shipped sqlite-wasm build is the conformance
  baseline. Keyless capture stays by `_dai_id`, never rowid mode.

     setting aside the newest versions first, each column such a version
     shows going back to the value before it. It is flagged pending, naming
     what was proposed, what is shown, and the constraint. So the earlier
     edit stands and the later waits, as the earlier-born row keeps a UNIQUE
     slot. Writing the row resolves it on both copies.
   - The Python reader applies the same rule. A row no candidate admits is
     held as before.
7. **M06.** A moves 10 between two accounts in one transaction; B sets the
   first account's balance.
   - **Before:** failed. The second account's +10 was settled alone.
   - **Fix, the policy:** the effect group stays together, and the group is a
     save. A changeset does not record the transactions inside one capture
     epoch, so the whole save is the conservative group. Where a row a save
     wrote is pending (every version a same-column conflict names, the
     proposal a constraint conflict set aside) or held, every other row
     where that save's change is still current is pending too, naming the
     save (`group`) and the rows it waits on (`with`). Recomputed after every
     projection, so a resolution clears it.
   - The Python reader agrees. The coupled test saves each table separately,
     and the real-runtime merge test reads the conflict's own flag.
8. **D02.** INSERT OR REPLACE over a UNIQUE name deletes a parent whose child
   cascades and fires a trigger. Run from both copies.

     D and I, child D, the trigger's row). The apply failed when the new
     row's author range sorted below the old row's: placed in key order, the
     new row met the slot still held by the row its own save deleted, and
     was held. The receiving copy showed no parent.
   - **Fix:** rows whose state is deleted are placed first. One parent, no
     child, one trigger row, on both copies, both orders.
9. **K06/K07.** B writes an explicit id in A's range above A's counter, then
   deletes it.

     live and on a copy restored from A's stored bytes, and the one after it
     would reuse the deleted id.
   - **Fix:** the counter rises past every id in the range that any
     changeset carries, at ingest and at open. `docs/format.md` states the
     guarantee: unique and never reused within the range, rising there, and
     not table-wide AUTOINCREMENT.
   - **Weakened** (the open-time scan only): the restore half is red alone.
10. **T11/P02.** An imported schema hangs `evil` on `_cs_log` and puts other

### The rulings

  does not support is refused at execution, before any data is accepted under

### Part 1, red first

The tests are `tests/changesets/review-1d.spec.ts` (node) unless named.
"Red" is the test against the runtime before its commit.

1. **1d-H1, runtime names.** One check, `runtimeNamed`, folds Unicode
   compatibility forms and case, and serves the authorizer, the open-time
   trigger drop, the capture filter and the adoption list.
   - **Red:** `evil_case` on `"_CS_LOG"` survived open and wrote six rows under
     the save; seven case-variant or fullwidth creations were allowed.
2. **1d-H2, DDL and the save that cannot succeed.**
   - A script holding ALTER TABLE or DROP TABLE runs statement by statement
     (split where `sqlite3_complete` ends one). Each such statement closes the
     epoch first (inside the application's transaction, its log row is written
     in that transaction), runs with the table it changes left out of the
     session, and is followed by a new epoch. One prepared outside exec is
     refused by the authorizer.
   - The runtime's records follow: a renamed table or column takes its history
     and is recorded (`_cs_shape`), so a change made under the old name lands
     under the new. A table made since the last save is not captured row by
     row; the next save logs it by its difference from the history its name
     has. So SQLite's twelve-step rebuild logs only what it changed (Map
     became Atlas: one update, no copied row), a new table logs its rows, and
     a dropped table logs its rows' deletes.
   - A copy without the table holds the row, flagged, until it makes it; a
     dropped column keeps its merged values in the cells.
   - Keys are stored as exact text (`keyText`); a key past 2^53 travels.
   - P3: a save failure no retry cures (the session cannot read back what it
     holds, a value cannot be encoded, text that is not UTF-8) sets
     `Changes.refusal`. Later writes are held by the authorizer, saves and
     merges apply nothing, the frame stops retrying, and the host shows
     `SAVE_REFUSED` as it is.
   - **Red:** every row of the review's table (rc=17, "Do not know how to
     serialize a BigInt"). The real-runtime P3 test is
     `runtime.spec.ts` test 8.
3. **1d-H3, keys that can be NULL.** A single key of integer affinity, by
   SQLite's rule over the type it reports (INT, BIGINT, INT8, UNSIGNED BIG
   INT, inline or table-level, NOT NULL beside it), takes ranged ids. Every
   other natural key in a rowid table gets runtime triggers that refuse a
   NULL before insert and before an update of its columns.
   - **Red:** `k_int` kept NULL ids.
4. **1d-H4, storage classes.** A REAL JS cannot hold as one (no fraction, or
   infinite) is a `Float64` from capture to apply: read by its SQLite type,
   encoded as a CBOR float64 (`decode(…, { floats: true })`), stored and
   written through `CAST(? AS REAL)`. An empty BLOB, which the session read as
   NULL, is read as one. A key's identity is exact for every class and equal
   where SQLite takes two keys for one row; its birth spelling is kept in
   `_cs_spell`.
   - Found on the way: sqlite-wasm binds a whole number past the int64 range
     as 0 (1e300 arrived as 0.0), so such a REAL is bound as its text.
   - The Python reader follows the same key text, using JavaScript's number
     layout (`js_number`, checked against Node on 9,013 values), and the dump
     both compare shows a whole REAL as `<real 1>`.
   - **Red:** Infinity refused the document at the save (P3 as a backstop);
     with the reader's `<real …>` removed, the M15 scenario failed.
5. **1d-H5, collations.** A key's identity folds each text part as its
   column's collation compares it, read from `pragma_index_xinfo` (NOCASE:
   ASCII letters; RTRIM: trailing spaces). A row is written under its
   earliest-born spelling, key column included wherever one key can be held
   under two spellings (a folding collation, or a key column with no type).
   The kit's views compare by the same identity through `dai_key()`.
   - Found on the way: the first fix rewrote the key only when the birth
     spelling differed from the identity, so a copy holding REAL 1.0 kept it
     when INTEGER 1 was born first. It showed only in one author order; the
     test now runs until it has seen both.
   - **Red:** `Bob@x` on one copy, `bob@x` on the other.
6. **1d-M1, 1d-M2, the lows.**

     trigger or index the application makes under a runtime name is refused.

**High: 5.** Three medium, three low.

- **1e-H1: a schema change inside a transaction that rolls back loses the
  edits saved nowhere yet.** The epoch's log row rolls back, and the capture
  was already cleared. This is the catalog's own S01 vector. Ran.
- **1e-H2: a schema change made through `prepare()` is never adopted.** A
  table made this way is never logged, even after a reopen. A trigger made
  this way is never stood down, and it fires on merged rows. Ran.
- **1e-H3: a key respelled under its own collation or storage class never
  travels.** The copy that respelled it reverts at the next merge of the
  row, with no flag. This is a regression from 1d-H5's identity fold. Ran.
- **1e-H4: logging by difference signs what a copy shows as its own edit.**
  After a table rebuild, an M02 constraint conflict is resolved in A's name
  to a value A never wrote. A row B deleted, which A kept because something
  referred to it, is re-inserted as A's. Ran.
- **1e-H5: SQLite's twelve-step DROP COLUMN, then another copy's edit of
  that column, takes the row out of the migrating copy for good.** Every
  other row of the held row's first save is then flagged pending. Ran.

### High

**1e-H1. DDL inside the application's transaction, then ROLLBACK.** R-S's
boundary logs the open epoch "inside the application's transaction … and
commits or rolls back with it" (`schemaChange`, `changesets.ts:1001`;
`closeEpoch`, `:1175`). `closeEpoch` then clears the capture. The epoch holds
everything since the last save, including committed work from before the
`BEGIN`. When the transaction rolls back, that work stays in the table, and
neither the log nor the capture holds it. Ran, from `base()`:
- the steps were `UPDATE items SET qty = 5 WHERE title = 'Bread'`
  (committed), `BEGIN`, an edit of Tent, `ALTER TABLE items ADD COLUMN
  extra TEXT`, `ROLLBACK`;
- result: A shows Bread `5`, `dirty: false`, and `save()` returns `null`.
  A's log never carries the 5, and B shows `1` after a merge;
- the same happened for `RENAME COLUMN` and for `DROP TABLE` (there,
  `dirty: true`, because the name is unsettled, but the 5 is still never
  logged);
- the same happened for each of the three with `SAVEPOINT sp … ROLLBACK TO
  sp`.

A migration that fails and rolls back is the ordinary shape of this. No
flag, no refusal. New in 1e: before it, a DDL left the capture alone (traced).
- **Direction:** inside a transaction, do not clear the capture at the epoch.
  Rotate it at the commit, or keep the closed epoch's ops until the
  transaction ends and log them again if their row did not survive. Or
  refuse ALTER and DROP TABLE while the application holds a transaction (R-V).

**1e-H2. `prepare()` skips adoption.** `statement` adopts after any exec
that moved `schema_version` (`changesets.ts:984`). The `prepare` wrapper
(`:882`) only settles a deferred apply. The capture filter leaves out a table
not yet adopted (`:696`). Ran:
- **A table.** `db.prepare("CREATE TABLE notes (id INTEGER PRIMARY KEY,
  body TEXT)").step()`, then an exec insert of two rows:
  - the ids were `1` and `2`, not ranged, and `_cs_keys` has no row;
  - `save()` returned `null`;
  - B, with the same table made by exec, shows only its own row. No flag.
  - A later exec schema change adopts the table, and the next save logs it
    by difference.
  - A reopen first adopts it as a table that was already there: `before
    reopen` was never logged, and only `after reopen` reached B.
  - The NULL-key guard (1d-H3) is missing too.
- **A trigger.** `db.prepare("CREATE TRIGGER items_dup AFTER INSERT ON items
  BEGIN INSERT INTO audit … 'dup'; END").step()`:
  - its text was left unguarded (`guarded: false`);
  - B's merged `Soap` fired it on A: `dupOnA: ["dup"]`, `dupOnB: []`;
  - `dirty: false`, and `converged: false`. This is 1b-H1 and 1d-M1's class.

`watch` treats a statement the application prepares as an ordinary route
(1d-L3). `selectValue` and the other `select*` helpers prepare through it too (traced
in sqlite-wasm's oo1).
- **Direction:** after a step that moved `schema_version`, run what
  `statement` runs.

**1e-H3. A respelled key.** The identity folds a key's text by its
collation, and a REAL with no fraction to the integer it equals
(`identity`, `changesets.ts:2074`; `keyPart`, `:148`). A row is written back
under its earliest-born spelling (`spellingOf`, `:2222`). An UPDATE that only
respells the key is an insert under the same identity, so it is never the
row's spelling. Ran:
- **The ordinary case.** `people (email TEXT PRIMARY KEY COLLATE NOCASE)`,
  and on A, `UPDATE people SET email = 'Bob@X.com' WHERE email =
  'bob@x.com'`:
  - after the merge, B shows `bob@x.com`;
  - B then edits the name. Once that merges back, A shows `bob@x.com` /
    `Robert`. A's correction is gone from A too, and `converged: true` with
    no flags.
- **Storage class.** The same happened for `nums (k PRIMARY KEY)`, `1` to
  `1.0`: after the round trip, A shows `integer`.
- **Composite keys.** `(x COLLATE NOCASE, y)`, in a rowid table and in a
  WITHOUT ROWID table, `'Key'` to `'KEY'`:
  - after A's save and B's merge, A shows `KEY` and B shows `Key`;
    `converged: false`, and no flag;
  - with a concurrent edit of `v` on B, both copies end on `Key`, with `v`
    pending.

Catalog M16 asks to "preserve original value spelling separately from
identity comparison". This was a regression, traced: before 1d-H5's fold, the
identity was the spelling, so a respelling travelled as a delete and an
insert.
- **Direction:** a row's spelling is its latest-born existing version's, not
  its first. Or record a respelling as an op on the key and order it like a
  column.

**1e-H4. A rebuild's difference is signed as the copy's edit.**
`unsettledChanges` (`changesets.ts:1695`) compares what the table holds with
`stateOf().values`, the latest heads, and logs each difference as the
author's. Two states the runtime itself puts in the table differ from those
heads. Ran:
- **M02.** `spans` has `CHECK (start <= finish)` and starts at (0, 10). A
  sets `start = 8`, B sets `finish = 5`, and the copies exchange.
  - Both show `(0, 5)`, flagged pending. `withinConstraints` set A's
    proposal aside.
  - A then rebuilds `spans`: new table, copy, drop, rename.
  - The save logs `["spans", "[1]", "start", "<A>:3", 0]`. After the
    exchange, both copies show `(0, 5)` with no flags.
  - A wrote 8. The rebuild signed 0 as A's, and resolved the conflict.
  - Without the rebuild, the same run keeps `pending` on both copies.
- **Kept-referenced.**
  - B deletes the category Food (clearing Bread's reference first), while A
    inserts Jam under Food.
  - On A, Food is `kept-referenced`.
  - A rebuilds `categories`. The save logs Food's existence, `name: Food`
    and `colour: null` as A's new version, re-asserting a row B deleted.
- **A same-column conflict** (qty 2 against 3) across the same kind of
  rebuild logged nothing and stayed pending. The shown value is the head.

The catalog's provenance rule is that runtime state must not become newly
authored local change. Twelve steps is the migration shape Build 1e
supports. New in 1e (traced: before 1e, a rebuild failed the save, 1d-H2).
- **Direction:** compare against what this copy last showed. That is the
  placed row (the candidate written, a kept row as kept), not the heads. Or
  carry a pending or kept-referenced row's flag across the rebuild, and log
  nothing for it.

**1e-H5. Twelve-step DROP COLUMN, then another copy's edit of it.** A table
made in the rebuild is renamed onto the old name from `uncaptured`
(`followSchema`, `changesets.ts:1084`). That route records no dropped column,
which the direct `DROP COLUMN` route does (`:1107`). So a merged value for
the column is written, fails, and `place` holds the row and deletes it from
the table (`:2297`). Ran, both with B's merge pending inside A's transaction
and with B's edit arriving after:
- A drops `note` in twelve steps. B sets Bread's `note` and `qty`.
- A's items are `Map, Rope, Stove, Tent`. Bread is held: `table main.items
  has no column named note`.
- A will never make `note` again. The row stays out of A's table, and A
  cannot edit it.
- Every other row A's first save wrote is flagged `pending` as its group:
  seven flags across categories, items and audit. `keepGroups` counts every
  head of a held row (`:2175`), its birth version included.
- B shows Bread with its edit.
- The direct `ALTER TABLE … DROP COLUMN` in review-1d keeps the value in
  the cells and holds nothing.

This is S05's shape: an older copy edits what a newer one migrated away.
- **Direction:** when a rename from `uncaptured` replaces a table, record
  the columns that table had and the new one lacks as dropped. Contend with
  a held row's own versions only, not with the versions it was born with.
