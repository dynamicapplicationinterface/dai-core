### What landed

For every document the compiler builds with no session policy:

1. **Capture.**
   - The compiler appends the changeset log to the schema:
     `-- dai:replicated CREATE TABLE _cs_log (payload BLOB NOT NULL)`
     (`src/changes-log.ts`, `src/core.ts`). So the document is an ordinary
     version 4 replicated document that `requires` authorship and
     replicated, with no new manifest field and no new capability.
   - The frame starts the session extension once the schema block has run,
     before the seed blocks (`startChanges`, `src/runtime/bootloader.ts`).
   - Every save, automatic or explicit, captures first, then seals, then
     saves (`captureSave`). The changeset is one `_cs_log` row, written by
     `createEntity`, so it is the payload of an ordinary signed batch.
     Batches, seq, floors and equivocation are unchanged, and
     `src/replicated-batch.ts` verifies as before.
   - A merge captures this copy's unsaved changes before it admits
     anything.
2. **Keys** (`src/changesets.ts`).
   - An INTEGER PRIMARY KEY is rewritten to an author-ranged id. The author
     index is in bits 32 to 52, the counter in bits 0 to 31, and the
     largest id is 2^53−1.
   - `last_insert_rowid()` is overridden.
   - A text key takes a uuid.
   - A table with no primary key is keyed by a ranged rowid. The session
     extension's `SQLITE_SESSION_OBJCONFIG_ROWID` captures it.
   - A literal id is the lint finding `literal-id` (a warning), whose fix
     says to omit the id.
   - **A.** The author index is 21 bits of the author id, never 0, until
     R-E's enrollment exists. Two authors of one document share a range
     with probability about n²/2^22. If they do, nothing is lost: the same
     id from two authors is one row, column-merged and flagged.
3. **Merge policy.** The spike's literal policy, ported as written:
   - different rows merge, and different columns of one row merge;
   - the same column written concurrently keeps both values, shows the
     later by (lc, author), and marks the row `pending`;
   - delete against update keeps the row, flagged `delete-conflict`;
   - a later local edit to a flagged row clears the flag on every copy.
   - The flags are rows of `_cs_flag(tbl, pk, kind, detail)` in the stored
     document, which the host can read from the bytes it holds. There is no
     sheet yet.
4. **Runtime rules.**
   - Seed blocks run once, at document creation (`runSeedsOnce`, recorded
     in `_dai_meta`). A copy that arrived carries the record, and its rows
     come from the log.
   - App triggers stand down while merged rows are applied: they carry
     `WHEN dai_projecting() = 0`, added when a table is adopted.
   - `PRAGMA foreign_keys = ON` at open.
     - **F.** No example declares `REFERENCES`: `grep -ci references` over
       every `examples/*/schema.sql` is 0. So none breaks, and none needed
       fixing.
     - The full suite and the ten apps ran with it on.
5. **Model file.**
   - `src/rules.ts` → `RECIPE` teaches one shape. Gone: the shape
     questions, the shared-table and session constraints, the surface, the
     views, the markers, and the two shared examples.
   - `IDS-FROM-THE-RUNTIME` is new. `SEED-IDEMPOTENT` (id kept) now says a
     seed runs once.
   - The packing-list example seeds without ids.
   - 146,463 bytes to 32,012.
   - Session policy is the host's. The chess fixture builds through the
     policy layer unchanged; `tests/changesets/authoring.spec.ts` holds its
     tables, session and `requires`.
6. **Readers.**
   - The Python reader gains `conformance/reference/dai_changes.py`. After
     `dai_merge.py` admits the log, it rebuilds the application's tables
     from the admitted log alone, never from the runtime's bookkeeping.
     - **F.** `tests/changesets/python-reader.spec.ts`: it equals the
       runtime's tables, flags and held rows in all 11 scenarios, both
       directions.
   - The Rust reader is not touched (R-P).
     - **F.** `cargo run --release --manifest-path conformance/readers/rust-merge/Cargo.toml -- conformance/merge`:
       "123 of 123 passed".
     - **F.** `python conformance/reference/dai_merge.py`: "123 merge

### What the full suite found, and what was done

The first full run on this branch: 1,357 passed and 41 failed on
Chromium before it was stopped, with Firefox repeating them. The
failures, by kind:

1. **Real defects, fixed.**
   - **"unknown function: dai_id()" on reopen** (`runner.spec.ts`,
     `sectioned-mount.spec.ts`).
     - A schema block that inserts, guarded, on every open
       (`INSERT … WHERE NOT EXISTS`) failed on reopen.
     - Cause: SQLite resolves a stored key's `DEFAULT (dai_id(...))`
       when it prepares the statement, and the runtime's functions were
       registered only when capture started, after the schema block.
     - Fix: `stageChangeFunctions` registers them first.
   - **An offline reopen fetched the merge module**
     (`offline-second-open.spec.ts`, `hint-and-install.spec.ts`).
     - Every document with the log waits for the write rules at open.
       The service worker never precached the merge module, which only
       shared documents used to fetch.
     - Fix: `sw.js` precaches it under its digest name, written in by the
       build like the confusables table.
2. **Budgets that moved, raised with the reason in the test.**
   - **Link size.** The compact carrier and the inline link were under
     4 KB for the chore chart and the packing list. With the log's
     rewritten declaration in the page they are 7.6 KB, and the budget is
     now 8 KB (`inline-carrier.spec.ts`, `inline-link.spec.ts`).
     - **I.** The rewrite is the same text in every document. A carrier
       dictionary that held it would win most of this back, but a
       dictionary change is a vector change (R-P), so it waits.
   - **The model file's budget** fell from 145,000 bytes to 33,000.
3. **Paths that changed on purpose, so the old path is now built on
   purpose.**
   - Each spec here tests a plain document as every compiler built it
     before today. Those documents exist, and R-P keeps their host paths
     in CI.
   - They build with `changesetLog: false`, a compiler option for tests
     that is not in the model file:
     - `other-tab-copy` (the four "document without shared tables"
       cases);
     - `returning-document` (whole-copy succession);
     - `send` and `share-and-keep-sentences` (the share card that leaves
       entries out);
     - `trust-consent` (the pin speaks before the held record);
     - `reference-link`, `rebuild-refused` and `succession`.
   - What each of those paths does with the log is a finding:
     - **F. A held document re-opened from a link** shows the merge card
       ("Open in my copy … What this link carries is added to your copy")
       instead of opening with no card (`reference-link`). This is
       replicated behavior today, and close to Gate B's B1.
     - **F. A rebuild under the same id** is offered as a merge, and then
       refused as another release (`rebuild-refused`).
     - **F. A new release of a plain document no longer replaces the old
       one with its data** (`succession`): "These two copies come from
       different releases of this app, so their games cannot be combined."
       Today two releases of a replicated document cannot merge
       (SIGNED_VIEW_MISMATCH), so the data of a document with the log does
       not carry into its next release until successor authority (R-I)
       exists. **This is the largest cost found.** Before today a plain
       document's release succession worked, with migrations.
     - **F. The V1 walk's update step fails on WebKit, the only engine it
       runs on** (`v1-walk.spec.ts`, "open, write, reopen, update or not,
       and share"). It passes on main.
       - It is left red on purpose, not built around.
       - The successor inherits the predecessor's database, whose log is
         signed under the predecessor's document id.
       - The phone flow's relaunch at the document's address offers it as
         a merge ("Open in my copy"). Then "This could not be added to your
         copy of Beach trip, so it was not opened, and nothing on this
         device was changed."
       - **I.** The authorship layer binds every batch to its document id,
         so history does not cross a release that takes a new id. This is
         R-I's question, not a Build 1 fix.
       - A host change that skipped the card when the arrival carries no
         database was tried, and only moved the failure to the merge. It
         was reverted.
     - **F. The share card of a document with the log** includes the
       entries by default, as a shared document's does (`send`,
       `share-and-keep-sentences`).
     - **F. A share in the first second after opening** is refused with
       "The latest changes here could not be signed and saved, so this was
       not sent. Try again in a moment." (`sender.spec.ts`).
       - The flush waits on the first seal, which landed about 3 s later.
       - **A.** The cause is unconfirmed. It looks like the sign waiting
         on the library lock during a first open.
       - Nothing is lost. The same share made after the first save has
         landed succeeds: the test passes with a 5 s wait, and now waits for
         the first save, since its subject is what the link carries.
4. **Registries.**
   - The three new refusal codes (`CHANGES_CAPTURE`,
     `CHANGES_KEY_UNREWRITABLE`, `ID_RANGE_EXHAUSTED`) are in
     `src/refusals.ts`, the wire list and the host-bridge table.
   - The model-file spec (`tests/rules.spec.ts`) now holds one shape.
   - The website's staged runtime is restaged, the impact map rewritten,
     and the current host retained.
