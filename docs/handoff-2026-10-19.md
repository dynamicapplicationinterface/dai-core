### What landed

For every document the compiler builds with no session policy:

1. **Capture.**
   - The compiler appends the changeset log to the schema:
     `-- dai:replicated CREATE TABLE _cs_log (payload BLOB NOT NULL)`
     (`src/changes-log.ts`, `src/core.ts`). So the document is an ordinary
     version 4 replicated document that `requires` authorship and
     replicated, with no new manifest field and no new capability.
   - The frame starts the session extension once the schema block has run,
     before the seed blocks (`startChanges`, `src/runtime/bootloader.ts`).
   - Every save, automatic or explicit, captures first, then seals, then
     saves (`captureSave`). The changeset is one `_cs_log` row, written by
     `createEntity`, so it is the payload of an ordinary signed batch.
     Batches, seq, floors and equivocation are unchanged, and
     `src/replicated-batch.ts` verifies as before.
   - A merge captures this copy's unsaved changes before it admits
     anything.
2. **Keys** (`src/changesets.ts`).
   - An INTEGER PRIMARY KEY is rewritten to an author-ranged id. The author
     index is in bits 32 to 52, the counter in bits 0 to 31, and the
     largest id is 2^53−1.
   - `last_insert_rowid()` is overridden.
   - A text key takes a uuid.
   - A table with no primary key is keyed by a ranged rowid. The session
     extension's `SQLITE_SESSION_OBJCONFIG_ROWID` captures it.
   - A literal id is the lint finding `literal-id` (a warning), whose fix
     says to omit the id.
   - **A.** The author index is 21 bits of the author id, never 0, until
     R-E's enrollment exists. Two authors of one document share a range
     with probability about n²/2^22. If they do, nothing is lost: the same
     id from two authors is one row, column-merged and flagged.
3. **Merge policy.** The spike's literal policy, ported as written:
   - different rows merge, and different columns of one row merge;
   - the same column written concurrently keeps both values, shows the
     later by (lc, author), and marks the row `pending`;
   - delete against update keeps the row, flagged `delete-conflict`;
   - a later local edit to a flagged row clears the flag on every copy.
   - The flags are rows of `_cs_flag(tbl, pk, kind, detail)` in the stored
     document, which the host can read from the bytes it holds. There is no
     sheet yet.
4. **Runtime rules.**
   - Seed blocks run once, at document creation (`runSeedsOnce`, recorded
     in `_dai_meta`). A copy that arrived carries the record, and its rows
     come from the log.
   - App triggers stand down while merged rows are applied: they carry
     `WHEN dai_projecting() = 0`, added when a table is adopted.
   - `PRAGMA foreign_keys = ON` at open.
     - **F.** No example declares `REFERENCES`: `grep -ci references` over
       every `examples/*/schema.sql` is 0. So none breaks, and none needed
       fixing.
     - The full suite and the ten apps ran with it on.

### High

**PR9-H1. Lost write in the merge's verify window.** The merge captures
first (`bootloader.ts:1511`, `captureSave(liveDb)`). Then it awaits
`verifyBatches` (`:1514`), commits, and projects (`:1543`). The application
can write during the await. Projection pauses the session
(`changesets.ts:193-202`, `:706-726`). But the session extension stores only
a row's first old value and reads the *current* value when the changeset is
generated (`:211`). So a row the application changed in the window is
captured at the next save holding the projected value. Its bases name the
remote version, as if the person had chosen it.
- Ran (P2). A and B share an item, "Tent". A sets "A-remote". B does what
  the frame does: save, verify, then `UPDATE items SET title = 'B-local'`
  inside the await, then admit and project, then save:
  `shownAfterProject: "A-remote"`. B's log now holds
  `["items", …, "title", "b14b…:1", "A-remote"]`. The cells hold "Tent",
  "A-remote" (A) and "A-remote" (B). **"B-local" is in no cell, on no
  copy.** `flags: []`.
- This breaks R-O ("never … discards conflicting changes"), with nothing
  flagged. The same leak follows any paused runtime write to a row the
  session already holds, including the save's own re-projection at
  `:585`, which runs after `take()` and so is safe today.
- The fix belongs to the frame: no application write may land between the
  capture and the projection. Alternatively, re-capture after the commit and
  before projecting.

**PR9-H2. R-F as written is not what was built.** R-F's text, set beside the
code:
- *"The same record, different fields: merge only where the app declared
  the fields independent."* Every column merges with no declaration
  (`stateOf`, `changesets.ts:748-758`). S2 (`merge-policy.spec.ts:44`)
  asserts the unconditional merge.
- *"An unresolved value is pending and does not feed calculations."* The
  later value is written into the application's table (`place` → `write`,
  `:830-832`), so every `SUM`, join and filter reads it. S3 (`:51`) asserts
  that one value shows.
- *Rejected: "showing an arbitrary winner with a flag."* Showing one value
  by (lc, author) with a `pending` flag is that alternative. R-F's evidence
  calls the author-id tie "to the person … arbitrary".
- R-F puts row granularity at V1.2 and checkpoint granularity at V1.0.

The review question lists "different columns merge; … shows later by (lc,
author)" as R-F. That wording is the spike's policy (handoff 19 October,
"Merge policy. The spike's literal policy, ported as written"). Either R-F is
amended to the spike's policy, or the policy changes. Today the code and the
ruling disagree, and the tests assert the code.

Per clause, the test and whether a weaker implementation would pass:

| Clause | Test | Weaker implementation passes? |
|---|---|---|
| Different rows merge | S1 (`:20`) | Yes, any merge does. Row ranges are asserted. |
| Different columns merge | S2 (`:44`) | No. Row-level last-writer-wins fails `missing`. |
| Same column keeps both, flags pending | S3 (`:51`), S5b, S5c | No for "keeps both" (`pending` detail holds both values). |
| …shows the later by (lc, author) | S3, S5c | **Yes.** Both accept either value (`toContain`). Any deterministic tie-break passes. |
| Delete vs update keeps and flags | S4 (`:79`) | No. The row and `delete-conflict` are asserted. |
| A later local edit clears the flag everywhere | "S3 resolved" (`:62`) | **Yes** for "clear every flag on the row at any save". No test edits a *different* column and checks that `pending` stays. |

**PR9-H3. `last_insert_rowid()` answers another table's id.** The override
(`changesets.ts:379-386`) keeps one slot, `{rowid, id}`, set by the
`_cs_id_<table>` trigger (`:458-460`). It returns the slot's id whenever the
connection's real last rowid equals the slot's hidden rowid. Hidden rowids
start at 1 in every table, so they coincide all the time.
- Ran (P1). `CREATE TABLE lists (id INTEGER PRIMARY KEY …)`,
  `CREATE TABLE tags (k TEXT PRIMARY KEY …)`, then in one transaction insert
  a list, then a tag: `{"lir":1666975591825409,"tagRowid":1,"listId":1666975591825409}`.
  Inside a transaction that inserts into two tables, `last_insert_rowid()`
  returns the first table's ranged id for the second insert.
- The `_cs_id_` trigger is not guarded by `dai_projecting()`. So a merged row
  also sets the slot, and the next application insert into a text-keyed or
  natural-keyed table can read a remote row's id.
- `IDS-FROM-THE-RUNTIME` tells authors to read ids back this way. The wrong
  id becomes a foreign key, and nothing fails.
- Two authors cannot produce the same id by this route. It is one copy
  reading the wrong id.

**PR9-H4. The counter is read before the log is projected.** `Changes` sets
`counter = highestOwnCounter()` in its constructor (`:392`). `startChanges`
calls `projectAdmitted()` after it (`bootloader.ts`, `startChanges`).
`mergedArrival` copies no application rows and no `_cs_` rows when the
arrival carries the log (`bootloader.ts:1633`). So a rebuilt copy counts
from an empty table and empty cells, then projects the author's own earlier
rows back in.
- Ran (P3), on the harness with the rebuild's state reproduced: app tables
  and `_cs_*` emptied, the log kept, the same author. After projection the
  ids are `[1831034752598017, 1831034752598018]`. The next insert fails:
  `UNIQUE constraint failed: items.id`.
- Every failed insert still advances the counter. So the first *n* inserts
  fail, where *n* is the author's highest counter. An id whose row was
  deleted is reused silently, and the old row's cells come back under it.
- This applies whenever a mount rebuilds an arrival that holds rows this
  author wrote: its own file, or a link back to it. That was traced; it was
  not run through the frame. The comment at `:416` shows the intent covers
  this.

### Medium

- **PR9-M1. A pending value cannot be resolved by keeping the value shown.**
  Ran (P4). After X/Y on one column, `UPDATE … SET title = <shown>` gives
  `saved: null` and `flags: ["pending"]`. The session records no change for
  an unchanged value, so the "new signed change that acknowledges both
  parents" R-F requires cannot be made for "keep this one". Build 2's sheet
  needs a write path that does not depend on a value changing.
- **PR9-M2 (Q4). The three runtime rules are set, not held.** Ran (P5).
  - `PRAGMA foreign_keys = OFF` from the application takes effect: an orphan
    insert succeeded. It lasts until the next projection turns it back on
    (`:723`).
  - `DROP TRIGGER "_cs_rowid_n"` takes effect: the keyless table's next row
    gets rowid 1, the same on every copy.
  - The `_cs_` bookkeeping tables (`_cs_flag`, `_cs_keys`, `_cs_held`) have
    no guards (`META`, `:64-72`), and the application wrote them.
  - Seed-once is runtime-enforced (`runSeedsOnce`), but by a `_dai_meta` row
    the application can delete.
  - Only `db.exec` is watched (`:396-404`). A table created through
    `prepare().step()` is never adopted: `keysOf` is null and `place`
    returns at `:821`, so its rows never reach another copy. That was
    traced.
  - Trigger guarding is skipped for any trigger whose SQL contains the text
    `dai_projecting()`, a comment included (`:491`).
  - This is the PR6-H1 class: the application drops the guard with one
    statement.
- **PR9-M3 (Q6). The direct path is undocumented, not refused.**
  `core.ts:552-553` sends any schema with a `-- dai:replicated` table or a
  session through the policy layer unchanged. Nothing refuses it. The lint's
  own fix text still names the marker (`lint.ts:302`).
  `authoring.spec.ts:67-73` checks only that `RECIPE` does not say it.
- **PR9-M4 (Q8). A new data format with no vectors.** The changeset payload
  `cbor([1, [table, key, op, new, old, bases, seen]…])` (`:572`, `:85`) and
  the projection policy are what a reader must implement to read a plain
  document's data. The Python reader gained `dai_changes.py` for that. The
  Rust reader cannot read it, and no vector fixes it. The 123/123 run covers
  the authorship layer, not this. Also new for hosts: `_cs_flag` as a
  host-read contract, and three refusal codes on the wire list. A ruling is
  needed on whether this is R-O's data interface or surface that R-P stops.
- **PR9-M5. Seeds duplicate across two first opens of one release.**
  Traced. Two contexts that each open the release before either has a copy
  of the other each run the seed block (`runSeedsOnce`), with ranged ids.
  This is spike B's case: one person, two contexts. They merge to two of
  every seed row. On main, idempotent fixed-id seeds converged. The rule now
  says to leave the ids out.

### Low

- **L1.** Equal values written concurrently are always `pending` (by
  design, S5b). Two copies that import the same backup with literal ids
  flag every cell.
- **L2.** The `orphan` flag's `pk` is `[rowid]` (`:900`), not the table's
  key format that every other flag uses.
- **L3.** A projection inside an application transaction leaves foreign
  keys on (`:711`), so an intermediate state becomes a hold or a throw. The
  merge opens its own `BEGIN`, so this path is probably unreachable. Traced.
- **L4.** `guardTriggers` finds the head with `\bWHEN\b` / `\bBEGIN\b`
  (`:492-497`). A column or table named `when` or `begin` breaks the
  rewrite.

### The questions

1. **The authorship layer is unchanged, by diff.** `git diff --stat
   c9da2e85 f661823d` over `src/replicated-batch.ts`,
   `src/replicated-rows.ts`, `src/replicated.ts`, `src/cose.ts`,
   `src/cbor.ts`, `conformance/merge` and `conformance/readers` is empty.
   `replicated-frame.ts` gains re-exports only (+16). What did change is
   which documents use the layer: every plain document now carries `_cs_log`
   and `requires` authorship and replicated (`core.ts:552-553`).
2. **Not literally R-F.** See PR9-H2, with the clause table.
3. **Two authors producing one id:**
   - Counter overflow is refused at 2^32 (`:430`).
   - Index collision is ≈ n²/2^22 by assumption, until R-E. A wipe that
     makes a new author draws a new index under the same odds.
   - The same author id in two live contexts (spike D's PRF same-secret)
     gives the same counter sequence: guaranteed collisions. That is R-E's.
   - A rebuilt arrival collides with its own author (PR9-H4).
   - An imported database with literal ids gives the same id on every copy,
     merged and flagged (L1).
   - `last_insert_rowid()` in a two-table transaction: PR9-H3.
4. **Enforced in the runtime, but not held.** See PR9-M2.
5. **The runtime's own triggers still fire.** `guardTriggers` touches only
   triggers on application tables, skipping names starting `_cs_` (`:491`).
   So the `replicated.ts` guards on `_cs_log`, `_dai_replica__*` and
   `_dai_batch__*` still fire during projection. `_cs_id_*` also fires
   (PR9-H3). `_cs_rowid_*` stands down. Foreign keys are off for the
   projection's savepoint.
6. **Reachable, not refused.** See PR9-M3.
7. **The cause is confirmed, by trace.** `core.ts:631` mints a new
   `documentUuid` for each build that does not pass one. `compile.ts:381`
   records the predecessor in `supersedes`. Batches verify against
   `mountDocument`. These depend on the same behavior: succession,
   rebuild-refused and the reference-link card (all listed in the handoff).
   PR9-H4's rebuild path does too.
8. **R-P.** No seat, roster, floor, session or vector change. One new format
   that needs a ruling: PR9-M4.
